The "1Password Access Requested — Allow tmux to get CLI access" Touch ID prompt is the **1Password CLI app integration**. The prompts are by design: re-authorization happens **once per terminal session AND again every time the 1Password app locks** (per https://developer.1password.com/docs/cli/biometric-security/). Kevin's fleet of tmux worktree sessions each counts as a fresh session → a prompt each, and any auto-lock revokes them all → prompt storm.

**ROOT CAUSE (confirmed 2026-06-29 via codesign):** Homebrew's tmux (`/opt/homebrew/bin/tmux` → Cellar/tmux/3.4_1) is **ad-hoc signed** — `flags=0x2(adhoc)`, `Signature=adhoc`, `TeamIdentifier=not set`. 1Password's app integration can't persist trust for an ad-hoc binary, so it re-verifies (Touch ID) on every new session/process. This is THE cause, independent of the MCP.

**Durable fix — DONE 2026-06-30 (staged):** created self-signed code-signing cert `tmux-codesign` in login keychain (Keychain Access → Certificate Assistant → Self Signed Root + Code Signing; shows CSSMERR_TP_NOT_TRUSTED under `find-identity -v` but codesign still uses it fine). Ran `codesign --force --sign "tmux-codesign" /opt/homebrew/Cellar/tmux/3.4_1/bin/tmux` → now `Authority=tmux-codesign`, `flags=0x0(none)` (no longer adhoc), verify passes. **STAGED**: takes effect only at next tmux SERVER restart (running server keeps launch-time adhoc identity). kill-server is destructive — default tmux socket is shared, so it kills the daemon + ALL worktree sessions + the main bridge session; the daemon prunes dead sessions from sessions.json on restart (wipes resume records). So either let it activate at a natural restart, or back up sessions.json first and resume from claudeSessionIds. ⚠️ `brew upgrade tmux` reverts to ad-hoc → re-run the codesign after upgrades.

**Pragmatic mitigations (no restart, no admin):** one persistent "op pane" (reuse one shell — keeps the ~10-min app-integration session warm, auto-refreshing), `op signin` once + verify with `op whoami`, batch secret reads while warm, treat connection errors as expired-session → one `op signin` retry, NEVER `tmux kill-server`. ~10-min idle lapse, ~12h hard expiry.

**2026-07-22 update — the WHAT-calls-op answer (treasury-specific), verified:** the ONLY `op` caller in the treasury repo is `bin/dev/with-dd-creds.sh` → `op read "op://treasury/Treasury Datadog/{credential,username}"`, invoked exclusively by `make dd-push|dd-pull|dd-drift|dd-import` → `ops/datadog/sync.mjs` (the **Datadog-as-code sync**). NOT the Makefile broadly (#8082 kept it lazy; no common target/hook/CI-local invokes it). It surfaces "recently" because of a burst of dd-as-code commits (#8289 drift-check workflow, #8236/#8191/#8169/#8149/#8141/#8135/#8123/#8111 dashboards+monitors, mostly INC-5201) — sessions codifying dashboards run `make dd-*` → `op`. Expected credential use, not an eager/stray read.
**Why it flares on a given day:** the `op` integration daemon recycles (verified 2026-07-22 10:38 via `~/.config/op/op-daemon.sock` + `op daemon` process timestamps) → flushes cached "Allow tmux CLI access" grants → next `op` call re-prompts.
**BEST FIX (verified 2026-07-22) — it's PROCEDURAL, no service account needed: don't run dd sync locally.** CI already does the whole datadog-as-code sync: `.buildkite/pipeline.rb` (wired by #7982) has `:datadog_validate` (runs `sync.mjs --dry-run && --drift-check` on PRs) and `:sync_datadog` (runs `sync.mjs` = apply, on merge to main), both gated on `ops/datadog/` changes. CI calls `sync.mjs` DIRECTLY with Buildkite secret DD creds — NOT `with-dd-creds.sh`, so **CI never touches `op`**. So local `make dd-push/dd-pull/dd-drift` (the only `op` callers) are dev-convenience only; the prompts are self-inflicted by running them by hand. Correct workflow = edit JSON → commit → PR (CI validates + applies). ⚠️ `docs/datadog.md` misleads: its "Update through code"/"new resource" flows say to run `APPLY=1 make dd-push` locally (lines ~45/57), contradicting its own "CI applies on merge" line — steer sessions off local dd sync and this whole prompt class disappears. sf8193's #8082 (lazy-load, Jul 2) was NOT reverted; it only removed SPURIOUS prompts on unrelated targets — real dd-* targets still prompt by design.

**tmux codesign fix STATUS (re-verified 2026-07-22):** the on-disk binary IS now properly signed (`codesign -dv /opt/homebrew/bin/tmux` → `flags=0x0`, not adhoc) — BUT the running tmux server started Jun 29 (pre-signing) and daemon restarts only cycle the `slack-daemon` *session*, never the *server*, so the fix has NEVER activated at runtime. A full tmux **server** restart (destructive — see above) is needed to make it take effect. Full Disk Access does NOT help (macOS file-access, unrelated to 1Password's CLI authorization).

**Fix to eliminate prompts:** use a **1Password Service Account** — set `OP_SERVICE_ACCOUNT_TOKEN` in the environment the tmux sessions/daemon inherit. `op` then authenticates via the token and never invokes the biometric/app integration → zero Touch ID prompts across all sessions (https://developer.1password.com/docs/service-accounts/). Tradeoffs: long-lived credential (store securely, don't commit), actions attributed to the service account not the user, scope the vault access tight. **Never handle the token value yourself — credential entry is prohibited; Kevin creates + places it.**

**Service accounts are admin-gated.** Created on the WEB only (1Password.com → Developer → Directory → Other → Create a Service Account; direct: start.1password.com/developer-tools/infrastructure-secrets/serviceaccount/) — NOT the desktop app. At AngelList (enterprise) Kevin likely lacks permission; docs say "if you don't see the option, ask your administrator." So full elimination needs IT/security to grant access or provision a token.

**No-admin immediate fix: set app auto-lock to "Never"** (Settings → Security → Lock after) on the trusted Mac. Key insight: prompts recur on two triggers — new terminal session AND every app lock. The lock is the storm: locking **revokes ALL sessions' authorization at once** → every tmux session re-prompts. Auto-lock-Never removes that whole class; each new session then prompts just once (first `op` use) until app restart. ~90% of the relief without an admin.

Caveat: the desktop-app MCP set up earlier (`/Applications/1Password.app/.../onepassword-mcp`, see [[claude-config-topology]]) uses the biometric app-integration path; the service-account route is the `op`-token model, so sessions must auth via the token rather than the app integration to go promptless.
