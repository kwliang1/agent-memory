BANK-1586 ("Auto-move linked tasks to Response Received on pending document upload"). Linear: Todo, XS, Nova Foundations, assignee Kevin, branch `kevinliang/bank-1586`. Origin: madison.stomberg1 Slack ask — when pending docs are uploaded for an entity with a linked task, auto-move the task to `Response Received` unless already in `Response Received`/`Verified`.

**It's an ipseity code change — NOT a Zapier zap, NOT a Flowdash automation.** The "Zap" Madison means is really `Alloy::SlackNotificationService.pending_documents_uploaded_message` in ipseity, driven by the Alloy application state machine.

Path today (ipseity):
- `app/models/alloy/journey/entity_application.rb:106` → `after_pending_documents` fires on Alloy transition to `pending_documents` (skips if `approved?`).
- Calls `Flowdash::Workflow::KycReview.get_tasks_by_entity_id(entity_id)` (workflow `jWaIEG`, filter `Entity Id`), falling back to `entity.related_entities`.
- Then `Alloy::SlackNotificationService.pending_documents_uploaded_message` posts to #alloy-alerts via Ipseity Bot (the "Unabled to find task" typo is our code).

Mechanism (verified vs flowdash repo): Flowdash tasks API `POST /api/v1/workflows/:id/tasks` = **upsert** and moves stage (`tasks_controller.rb:141` → `result[:stage_name] = params['Stage']`); data is `@task.data.merge`d so a minimal payload doesn't wipe fields. Workflow unique-id field is `Id`. ipseity client already has `Flowdash::Client.upsert_flowdash_task!('jWaIEG', {'Id'=>..., 'Stage'=>'Response Received'})`.

**The one real decision — which stages to protect.** Ticket literally says "move unless already in Response Received/Verified" — UNSAFE, would yank tasks out of Rejected/Suspicious LPs/Invalid/Inactive/Test/Duplicate/Verified Externally on a doc upload. Do NOT take the literal reading.
- `Stage#end_stage` boolean exists in flowdash (`flowdash/app/models/stage.rb:46`) but is NOT exposed over REST (only GraphQL) — the Bearer-workspace-key REST client ipseity uses can't read it.
- **BEST approach (refined, last state before reboot):** use the Tasks API `/tasks/active` endpoint = "tasks not in an end stage". ipseity client already supports it: `get_flowdash_tasks_with_filters(..., only_active: true)`. So fetch active tasks by entity id and advance those → terminal stages fall out automatically, no hardcoded protect-list to maintain, robust to ops adding new terminal stages. (Verified against docs served from flowdash repo `docs/api/tasks-api/index.md` + `docs/api/stages-api.md`; live URL behind auth gateway. Stages API returns `name` only — can validate casing but can't classify terminal-ness.)
- Skip a no-op self-move: `next if t['Stage'] == 'Response Received'`.
- Fallback if `/active` rejected: explicit allow-list of advance-from stages (seed from treasury's active set: In Progress, Needs Review, Needs Follow-Up, Time Sensitive, maybe Escalated) — strictly safer than enumerating terminal stages.

**OPEN QUESTION for Madison/Nick (only unresolved item):** are there any *working* (non-end) stages we must NOT pull a task out of? e.g. `Escalated` or an active compliance-review stage — `/active` only excludes stages ops marked `end_stage=true`, so a non-end in-flight stage would still be advanced. If yes → those few get an explicit skip on top of the active filter. If no → the active filter alone is the whole guard.

Pre-existing bug to fix in same PR: `slack_notification_service.rb:25` computes `filtered_tasks` (rejecting In Progress) but line 30 iterates the unfiltered `tasks` — dead filter today. Since we now want to advance In Progress tasks, align this.

Tests: stub `Flowdash::Client`, assert we upsert `{Id, Stage: Response Received}` only for active/non-protected tasks, skip protected, and that a move failure still posts Slack (per-task rescue so one bad task never blocks others or the alert). Add related-entities case. Low blast radius (writes only jWaIEG task stage).
