Ops question "does ipseity support updating an entityType?" (Trust→IRA conversion, 2026-08-06). **Yes, via one purpose-built destructive method — NOT the normal update path.**

- Method: `Entities::UpdateService.swap_entity_types!(entity:, new_entity_type:, region:, force:)` — `app/services/entities/update_service.rb:11-67`. Own comment: "HIGHLY destructive."
- REST surface: `POST /api/entities/swap_entity_types` (`config/routes.rb:127` → `app/controllers/api/entities_controller.rb:411-423`, permits `[:entity_id, :entity_type, :region, :force]`).
- **NOT** reachable via Prophet `entities:update` — that input schema has no `entity_type` field (`entity_prophet_api .../messages/entities/update.rb`; `EntitiesHandler#update` never passes it). No Nova client caller, no GraphQL, no UI — backend-only.

What it does (in a txn): destroys current identity_data + its current_address (carries over only `name`), destroys signatory/control-person/major-shareholder/grantor/individual **role join rows** (linked people survive, links don't), creates an empty new-type identity_data shell via `Entities::IdentityData::CreateService`, sets `entity.entity_type=`, `save!` (which auto-swaps kyc_aml_status type via `touch_kyc_aml_status`). NOTE: old-type kyc_aml_status row is NOT explicitly destroyed — a stale row may linger. IRAs have no own KYC status — they're KYC'd as an individual (person role).

**force gate (the key gotcha):** returns `false` (no-op) unless `force: true` if ANY owner already ran checks. Owners = `[entity] + control_persons + major_shareholders + signatories` (`:157-159`). "already ran" = `kyc_aml_status.try(:already_ran_identity_checks?) || .try(:already_ran_watchlist_checks?)` (`:161-164`), where each predicate = `identity_state != 'unchecked'` / `watchlist_state != 'unchecked'` (`identity_concern.rb:44`, `watchlist_concern.rb:48`). So an already-verified entity NEEDS `force: true`, and force overrides the "address destroy is safe because checks haven't run" assumption (`:41-44`) — you accept that risk.

Trust KYC status quirk: `KycAmlStatuses::UnitedStates::Trust` includes WatchlistConcern + RelatedEntitiesConcern but NOT IdentityConcern → it has `watchlist_state` but NO `identity_state`/`already_ran_identity_checks?` (trust identity verification is delegated to related people, who appear as separate owner rows). Use `.try` when probing, like the guard does.

**Console dry-run to decide force** (host repos can't boot — run in prod console). Map treasury customer_account → entity first: `CustomerAccount.find("<uuid>").entity_id` (treasury console). Then ipseity:
```ruby
entity = Entity.find(<entity_id>); region = Entity::US
owners = ([entity] + entity.control_persons + entity.major_shareholders + entity.signatories).uniq
owners.map { |o|
  s = KycAmlStatuses::FetchService.kyc_aml_status_by_entity_and_region(o, region)
  { id: o.id, type: o.entity_type, status_class: s&.class&.name,
    identity: s.try(:identity_state), watchlist: s.try(:watchlist_state),
    already_ran: (s.try(:already_ran_identity_checks?) || s.try(:already_ran_watchlist_checks?)) }
}
```
Any owner `already_ran: true` → `force: true` required. All `unchecked`/false → no force.

Aftermath of a force swap on a verified entity: blank new-type shell — must re-enter new-type identity data + re-attach the correct individual/roles, then re-verify. Related: [[bank-1586-response-received-plan]] (ipseity KYC), [[onboard-vehicle-accounts-spike]] (entity_type→identity_data mapping).

## Alternative: surgical DB/console conversion (preserves verification — big advantage over force-swap)
For the Trust→IRA case (2026-08-06), a hand-scripted conversion can PRESERVE the existing verified person's KYC and avoid re-verification, which force-swap cannot.

**Key mechanic — IRA has no own KYC status.** No `kyc_aml_statuses_united_states_iras` table (only person/company/trust — verified via `ls app/models/kyc_aml_statuses/united_states/`). `Entity#united_states_kyc_aml_status` (`entity.rb:199-210`) has no `when IRA` branch → returns nil. `touch_kyc_aml_status` (`entity.rb:478`) only builds person/company/trust. An IRA is "verified" PURELY by having a `Roles::Individual` (`entity.rb:64 has_one :individual_roles_as_entity`) pointing at an already-verified person: `Entities::VerificationService.verified_ira?` (`verification_service.rb:97-102`) = `entity.individual` present && `verified_person?(individual)`. Watchlist/Alloy/identity all look through `entity.individual` for IRAs (`verifications/watchlist_service.rb:18-20,40`, `alloy_service.rb:16`).

**Conversion steps (one AR console txn):** (1) `entities.entity_type` trust→ira; (2) create `IdentityData::Ira` (name, tax_id, ira_type ∈ TRADITIONAL/ROTH/SEP/SIMPLE, custodian_name, current_address copied from trust); (3) **create `Roles::Individual` entity→verified person — LOAD-BEARING** (without it verified_ira? is false, distribution stays blocked); (4) drop unwanted person's role links; (5) clean up orphaned trust rows (`identity_data_trusts` + its wealth_sources/screenings/address, `kyc_aml_statuses_..._trusts`). Because the target person is already verified, verified_ira? is true immediately → no re-KYC.

**Landmines:** (a) **Encryption** — `tax_id` etc use `encrypts`, KYC/identity rows assign `encrypted_key` in before_validation → MUST go through ActiveRecord in a console, NOT raw SQL (raw writes corrupt encrypted cols + skip key). (b) **No event on a type flip** — the treasury-consumed lifecycle event (`entity_lifecycle_event_emitter.rb`) only fires from `KycAmlStatus::BaseConcern` (KYC-state changes) + name-change concern; NOTHING emits on an `entity_type` change → treasury won't auto-learn the entity became an IRA, so the trust-doc block may persist until treasury re-reads. OPEN: confirm treasury pulls `entities:show` on-demand vs caches, and whether a manual re-sync is needed. (c) Compliance sign-off (bypasses KYB confirm-roles).

Trade: force-swap = supported but re-KYC required; DB/console = preserves KYC (fast unblock) but manual multi-table AR surgery + propagation risk.

## venture side: InvestmentEntity.entity_type is a SEPARATE copy (must also update)
An entity_type conversion is cross-system. venture `InvestmentEntity` (`app/models/investment_entity.rb`) stores its OWN `entity_type` string (values: individual/firm/ira/trust/revocable_trust, `:66-67`), linked to the ipseity entity only by `entity_api_id`. It reads the ipseity type ONLY at create (`populate_entity_api_id :429-435`) → the ipseity flip does NOT sync back; update venture independently. Mapping 1:1: venture 'ira' ↔ ipseity IRA (`lib/ipseity/entity/types.rb:34`; both trust variants → ipseity TRUST). Update = plain `ie.update!(entity_type: InvestmentEntity::IRA)` — mutable string, only inclusion validation, no attr_readonly (`Indestructible` blocks deletes not updates). Nothing blocks →ira: firm_type validation gated on `firm?` (skipped), is_dao/is_fund already false for a trust. Gotchas: (1) slug regenerates on entity_type_changed (`should_generate_new_friendly_id? :462`); (2) `ira_account_info` (has_one dependent:destroy) is ALTO-IRA-specific (`is_alto_ira?=ira_account_info.present?`) — Equity Trust self-directed IRA isn't Alto, leave nil; (3) stale caches `kyb_submitted` (trust does KYB, IRA doesn't) + `cached_kyc_data_complete` (refreshes via ipseity→monolith `AngellistCallbacks.ipseity_entity_updated`). Sequence ipseity + venture flips close together so no flow sees them disagree. Kevin handling treasury propagation himself. **Prod-console write guard (reusable):** the ipseity/monolith production console (`lib/production_console.rb` PaperTrail) is READ-ONLY until you set an audit note via `oc("note")`. So call `oc("...")` once before running any write-bearing console script; every subsequent write is PaperTrail-audited.
