Treasury money-movement idempotency tokens in `Investment::Payments::TreasuryService` are currently amount-derived (`investment-payment-{kind}-{payment.id}-{amount.cents}` via the private `treasury_transfer_idempotency_key` helper). This is a known stopgap, not the real fix.

**Why amount-derived tokens are wrong (decided after analysis):** amount must be both stable across retries of one operation AND unique across distinct operations, and it satisfies neither. Two legitimately-distinct same-amount movements collide → Treasury silently dedups the second (false-dedup); and an amount that shifts between retries (threshold/commitment changes) produces a different token → no dedup → double-send. This hole exists on ALL paths: `transfer_funds!` (multi-installment capital calls), `refund_funds!` (multiple partial refunds), `complete_from_escrow!` (multiple sweeps). `initiate_pull!` (funding) is currently masked by the `return if payment.treasury_ach_pull_id.present?` boolean guard — but that same guard also blocks legitimate top-up pulls when a payment amount increases.

**The systemic fix (planned, NOT yet built):** a persisted `Investment::PaymentTransfer` model — one row per intended money movement, minted once in the same DB transaction as the state change that decides it. Its id IS the idempotency token (prefixed for readability), so retries reuse the row (same token → dedup) while distinct ops get distinct rows (no false-dedup); amount drops out of the key entirely. Store a SOFT reference to the resulting Treasury transfer id (backfilled from the API response) — NOT a hard FK, since Treasury is a separate service reached over HTTP/proto. This model also retires the `treasury_ach_pull_id` boolean guard and is the proper foundation for per-domain call-site updates (continuous_fund, lead mutations, investment_entities, punk_6529 — ~13 direct `Treasury::TransferService` callers that omit tokens today).

**Treasury facts:** `idempotency_token` is `string(255)` with a UNIQUE index on Treasury's transfer/ach_pull/etc. models. Keep tokens human-readable (no hash/cipher) — the gem's own convention prefixes them (`REPAY-`, `PASSTHROUGH-FEE-`). Underlying proto params that accept a token: `TransferCreateParameters` field 8, `RefundFundsToLPParameters` field 5.

**Status:** PR — angellist/venture#29587 (branch `kevinliang/fix-ach-funding-idempotency-collision`). Now namespaces BOTH movements via the `treasury_transfer_idempotency_key(kind, payment, amount)` helper: `:funding` → `investment-payment-funding-{id}-{cents}`, `:transfer` → `investment-payment-transfer-{id}-{cents}`. It re-adds the invest-transfer token that INC-4911 (#29412) introduced and #29581 reverted — but on the fresh `transfer-` namespace instead of the bare token. The collision was OBSERVED in prod (ACH-pull funding shared a token with the eventual on-platform transfer). Treasury dedups per-table (AchPull.find_by vs Transfer.find_by); the pull's token reaches the transfers table on settlement, which is how pull and transfer collided. Using a brand-new `transfer-` namespace (vs reusing the bare token) was a review finding — it closes the migration-window re-collision with pre-deploy bare-token rows and removes any dependency on the exact Treasury settlement-token format. `Treasury::TransferService.invest_funds!` regains an optional `idempotency_token:` kwarg. The in-flight double-pull migration risk (funding token format change) was knowingly accepted by the user (treasury team, oncall). The remediation scratch (`tmp/replay_stalled_transfers_scratch.rb`) intentionally uses the same `investment-payment-transfer-{id}-{cents}` token so a manual replay and the normal path dedup rather than double-transfer. Systemic fix remains the Investment::PaymentTransfer model.
