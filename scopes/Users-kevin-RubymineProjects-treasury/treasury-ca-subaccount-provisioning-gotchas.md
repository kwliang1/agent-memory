Verified facts for scripting treasury CustomerAccount (CA) + subaccount creation (2026-08-14, treasury@abc4ab830). Context: Bisher wanted a 2nd concurrently-active CA on the SAME owner entity as an existing CA (`2fb94810d7c643d7bbabb99817dab6f4`), with a JPM subaccount, for testing. Solution = shard by `account_purpose` (Kevin chose `RESERVE_ACCOUNT`).

**owner_entity uniqueness is NOT blanket** (`customer_account.rb:144`): `validates :owner_entity_api_id, uniqueness: {scope: :account_purpose, conditions: -> { where(account_purpose: INVESTMENT).where.not(owner_type: FBO) }, if: -> {!fbo?}}`. Only blocks two **non-FBO INVESTMENT** CAs on the same entity. FBO is explicitly EXCLUDED. Any other `account_purpose` → allowed. DB index `oeai_and_ap` is non-unique; no SSN/tax-id uniqueness in treasury (that's ipseity-side, and reusing the same entity never re-triggers it). Kevin's "just for owner_type===fbo" hunch was backwards — the guard excludes fbo.

**CreateService (`customer_accounts/create_service.rb`)** adds per-`(entity, account_purpose)` idempotency (lines 50-56): a repeat create returns the existing CA for ALL purposes, not just INVESTMENT. So different purpose = the escape hatch at both layers.

**TRAP — auto-subaccount ignores requested bank for non-FBO CAs:** `SubAccountRequests::InfoService.resolve_program!` (`info_service.rb:22-24`) routes non-FBO CAs to `resolve_non_fbo_program!` → always GHB Main (or FTB for intl), **ignoring `partner_bank_program_name`**. Only FBO CAs honor the requested program (`resolve_fbo_program!`). So `CreateService.create!(partner_bank_program_name: JPM)` silently opens Grasshopper, not JPM. To target a specific bank on a non-FBO CA, open the subaccount EXPLICITLY via `SubAccountRequests::CreateService.create!(customer_account:, partner_bank_program:, reason_type: NewAccount)`.

**JPM = DIBS-only + manual KYC + async.** Only JPM program is `PartnerBank::Program::DIBS_JPM_NAME` (=`DIBSApi::Constants::JPM_NAME`). `SubAccountRequests::StateService#process_dibs!` (`state_service.rb:252-259`): BNY/JPM submit a DIBS application keyed to `owner_entity_api_id` and WAIT for a completion webhook — subaccount is NOT live synchronously. Can raise `AccountOpeningProhibited`/`ApplicationValidationError` (dedup) → failed SubAccountRequest. (Non-BNY/JPM DIBS create inline.)

**TRAP — `update_verification!` (`concerns/customer_account/verification.rb:21-34`)** on an unverified→verified flip auto-calls `create_dibs_sub_account_if_applicable!` (Piermont Direct, gated on Flipper `new_domestic_lps_on_piermont_direct` + domestic person/company/ira) and `create_sub_account_for_previously_blocked_if_applicable!` (GHB; but guarded by in-flight SubAccountRequest + `sub_accounts.any?`). A CA has ONE active subaccount at a time, so this can open a COMPETING subaccount. When scripting a specific-bank CA, set `verified:` at `create!` time (mirrors system reserve/holding account creation) rather than calling `update_verification!`.

**TRAP — non-FBO CA display_name is NOT durably custom-settable.** `refresh_cached_names!` → `update_display_name!` (`display_name_management.rb:11-31`) overwrites `display_name` with the owner entity's legal name via `update_column :display_name, owner_identity_data.name` for non-FBO CAs (the `Rails.env.test? && !fbo?` early-return means it RUNS in prod; also fires whenever an associated identity's name changes). So a custom `display_name:` at `create!` only sticks if you (a) don't call `refresh_cached_names!` and (b) the entity name never changes. System reserve/holding accounts carry custom names only because they're `owner_type: FBO` (FBO display_name comes from `fbo_identity`, not the entity). Corollary: the reserve_account() name-collision worry is moot for a non-FBO CA — its name is the entity legal name, never `"Reserve Account (...)"`. When scripting, drop `refresh_cached_names!` if you want a custom label to persist.

**RESERVE_ACCOUNT is safe to reuse as a shard:** system reserve lookup `SystemAccounts::InfoService.reserve_account(program)` keys on `display_name == "Reserve Account (<program>)"` (`info_service.rb:64-67,162-164`), NOT on entity — so a custom display_name never shadows it.

**FBO path differs materially (learned when the source CA `2fb94810d7c643d7bbabb99817dab6f4` turned out to be FBO — "FBO Investors in AngelList", owner_type=fbo, entity `019a9d0c47dc7569ab4ecda1fdc6668a`).** (1) Line-144 uniqueness is SKIPPED for FBO (`if: !fbo?`) — no owner_entity guard at all, so sharding-by-purpose isn't dodging anything for FBO (still fine as a label). (2) FBO CAs REQUIRE an `fbo_identity` (`fbo_identity.rb`: validates `holding_account` + `beneficiary_name` presence; beneficiary_name encrypted; optional fund_lead_entity_id/mece_market_tag/is_ruv). A bare `CustomerAccount.create!` with owner_type:fbo passes validation (fbo_identity is `has_one`, not presence-validated) but is MALFORMED — breaks program resolution/display/DIBS. Build it via `CreateService` (which requires `beneficiary_name:` and calls `build_fbo_identity`) or `build_fbo_identity` manually mirroring the source. (3) For FBO, `resolve_fbo_program!` (info_service.rb:44-64) HONORS the requested program — BUT only when `fbo_identity.fund_lead_entity_id.present?` OR `source == NOVA`; otherwise routes to GHB Omnibus regardless of requested bank. So to force JPM on an FBO CA lacking a fund_lead, open the subaccount DIRECTLY via SubAccountRequests::CreateService (bypasses resolve_program!). (4) DIBS JPM app is keyed to `owner_entity_api_id`; if the entity already has a completed JPM SubAccountRequest, a 2nd may be rejected as duplicate.

**RESOLVED APPROACH (2026-08-17):** source turned out FBO w/ fund_lead → dropped the hand-rolled direct-build; final = one `CustomerAccounts::CreateService.create!(entity_id: '019a9d0c47dc7569ab4ecda1fdc6668a', source: 'angellist', account_purpose: RESERVE_ACCOUNT, owner_type: FBO, beneficiary_name: 'PropFund Testing Account', fund_lead_entity_id: '019a9d1788cd7b269bcf94abf51e65fc', partner_bank_program_name: DIBS_JPM_NAME)`. It builds fbo_identity, honors JPM (fund_lead present), runs update_verification!, is idempotent per (entity,purpose), standalone (not IVC-linked). Purpose RESERVE_ACCOUNT chosen w/ Bisher (petty-cash semantics), NOT because line-144 blocks INVESTMENT for FBO (it doesn't — 4 INVESTMENT FBO siblings coexist). Siblings 421420-423 got JPM via IVC provisioning, not fresh DIBS apps; this one WILL fire a fresh submit_application! (async, manual KYC, webhook — watch req state). Scratchpad: `create_propfund_reserve_jpm.rb` (final), `dry_run_bisher_reserve_jpm.rb`, `inspect_fbo_source.rb`. Do NOT wrap a direct SubAccountRequest in an outer txn — its Temporal workflow reads the row by id and needs it committed.
