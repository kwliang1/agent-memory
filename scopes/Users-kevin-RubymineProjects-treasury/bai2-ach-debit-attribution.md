Verified 2026-07-23 (cedar). Attributing a BAI2 `PreviousDayBai2File` ACH-debit line like:
`type 469 "Miscellaneous ACH Debit", text "AngelList Payment 11n5mbmxak9b5s0 FBO AngelList Clients", bank_reference "026198003152571"`.

**Mechanism (code):** `Bai2SyncFiles::OtherProcessingService.process_cross_debit_transfers!` (`other_processing_service.rb:48`) selects disbursement-account debits (MISC_DEBIT/ACH_DEBIT type codes) whose text starts with an AngelList settlement prefix (`ANGELLIST_SETTLEMENT_TRANSACTION_PREFIXES` = "AngelList Payment" / "AngelList Manage Payment" / "FBO AL Customers Payment", in `processing_service.rb:15`), then matches them **by amount_cents** to either a legacy `CrossTransfer.from_svb` or a V2 `Transfer` (`match_transfer_v2` → `Transfers::V2::StateService.complete!`). "FBO AngelList Clients" = `PartnerBank::SVB_ACCOUNT_HOLDER_NAME` (SVB concentration acct).

**Attribution recipe (the two IDs on the line pinpoint ONE record):**
- text middle token (`11n5mbmxak9b5s0`) = the TreasuryPrime **initiating** id, stored as `ach_<token>` in `Transfers::Metadata.initiating_payment_processor_transfer_id`.
- `bank_reference` = the SVB **receiving** id in `Transfers::Metadata.receiving_payment_processor_transfer_id`.
- Query: `Transfers::Metadata.where("initiating_payment_processor_transfer_id LIKE :t OR receiving_payment_processor_transfer_id LIKE :t", t: "%<token>%")` → its `transfer`. Confirm with `Transfer.where(amount_cents:)`. (Legacy: `CrossTransfer` string cols `treasury_prime_ach_id` etc.)
- Direction lives on metadata `from_sub_account`/`to_sub_account`, NOT on Transfer columns (Transfer#from_sub_account raises). `init=TreasuryPrime` ⇒ GHB/Piermont side; `recv=SVB` ⇒ SVB side. An SVB→GHB move shows as an ACH **debit on SVB's** BAI2 (SVB is payer), originated by TP (debit-pull).

**The flow that GENERATES these (incoming-wire return, GHB↔SVB round-trip):** when `IncomingWires::StateService#return!` (`state_service.rb:314`) returns a wire whose `original_sub_account` (bank where it landed, e.g. SVB) ≠ the account's current active sub (e.g. GHB), it creates Transfer "Returning wire funds to original bank" (active→original, GHB→SVB). On that transfer's completion the generic hook `Transfers::V2::StateService#forward_funds_to_active_sub_account_if_needed!` fires and auto-creates a FUNDS_MIGRATION "Forwarding funds to active sub account for transfer <id>" (original→active, SVB→GHB). Net cash zero, but produces a same-amount SVB-side ACH debit ~1 day later.

**Why the hook fires (NOT balance-check driven):** it's an unconditional step in `Transfers::V2::StateService.complete!` (`state_service.rb:120`), which runs on EVERY transfer→Completed. `complete!` itself is invoked here by BAI2 matching (`match_transfer_v2` → `complete!`, `processing_service.rb:61`) when the SVB file shows the return leg landing. The hook only no-ops via 3 early-returns (`state_service.rb:303-306`): `destination.cross_tp_instance?`, `active_sub_account == to_sub_account`, or `funds_migration_transfer? || mirror_transfer?`. For a wire-return transfer all three are false (to_sub is the inactive original bank; category is RETURN, NOT exempted) → it forwards. **Likely-bug hypothesis raised to Kevin:** the exemption list should probably also cover `category: RETURN`, else wire-returns thrash GHB→SVB→GHB. Related to [[funds-migration-autoforward-stranding]] and [[treasury-prod-console-access]].
