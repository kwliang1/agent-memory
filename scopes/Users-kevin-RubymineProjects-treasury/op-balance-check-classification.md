Balance-check classification is pure over the persisted `in_progress_details` JSON snapshot. Rows are minted by collectors in `app/services/customer_accounts/balance_service.rb` (`external_payment_processor_balance`, `collect_*` methods) and classified by predicates historically on `BalanceCheck::Record` (extracted to `BalanceCheck::Classification` by BANK-1859) — `match_kind` (incoming :full_sum/:confirmed/:subset), `explained_by_migration?` (signed netting), `explained_by_outgoing_debit?` (treasury-ahead subset). Consumers: `BalanceChecks::DifferenceService` (mint) + GraphQL `Types::BalanceChecks::RecordType` (read). The three settle predicates are deliberately NOT unified (a prior `.abs` unification hid a direction-blind masking bug).

**OutgoingPayment ledger timing (the BANK-1862 gap):** an OP's main debit posts to the CA ledger ONLY at `OP#complete!` (`app/services/outgoing_payment/state_service.rb` ~757-795 — a direct `LedgerEntry`, NOT a Transfer; `Simple` plans have zero funding steps). The bank is debited earlier, at execution submit (`execution.mark_submitted!`, set atomically only on a successful bank API call → `submitted_at` present == bank acted). So an OP in `state: Processing` whose execution is submitted-but-not-completed leaves the bank ahead of the ledger = a **treasury-ahead gap** (internal > external) that was unclassified → false balance-check break ("loss of signal", Harsohail 2026-08). Pre-submit states (queued/requested/in_compliance_review/held/awaiting_ops_approval, and pre-submit Processing) move neither ledger nor bank → no gap.

**Non-atomicity gotcha:** `execution.record_bank_state!('completed')` and `OutgoingPayment::StateService.on_execution_completed!` (→ `complete!`, posts the LE) are two SEPARATE non-atomic transactions at every webhook call site (`treasury_prime/webhook_service.rb`, `bai2_sync_files/wire_processing_service.rb`). So there's a real window where `execution.state == completed` but the OP is still `Processing` and no LE exists — gate on `OP.state == Processing` (not execution state) to catch it.

**BANK-1862 fix (collector-only, PR #8631 on main):** `collect_pending_outgoing_payment_debit_details!` (in `customer_accounts/balance_service.rb`) iterates `OutgoingPayment::InfoService.bank_debited_unledgered_for(active_sa)` and emits a non-adjusting outgoing-debit row (`record_type: 'OutgoingPayment'`, `adjustment_cents: 0`, `funds_migration: false`). The existing BANK-1847 `explained_by_pending_outgoing_debit?` classifies it — zero classifier change. SLA reuses per-rail transfer `submitted_to_completed` thresholds (`SlaPolicy`, `PaymentSource::Transfer`) via `execution.processor` + `payment_method` — a stand-in until a dedicated OP payments-health SLA.

**Gate is PROCESSOR-AWARE (mirrors transfer_v2_pending_outgoing_adjustment), not "any submitted":** the bank-debit point differs by processor — DIBS debits at execution `Submitted`; TP/SVB NOT until they process. Cursor Bugbot caught the naive "submitted == debited" version as a TP over-explain risk (a TP OP submitted-but-not-yet-debited could subset-match and falsely settle a real break). So `bank_debited_unledgered_for` selects `OutgoingPayment.where(egress_sub_account:, state: Processing)` joined to an execution where (DIBS: state ∈ [Submitted, Processing, Completed]) OR (non-DIBS: [Processing, Completed]), `submitted_at` NOT NULL. KEY: OP executions never reach `Processing` today (`begin_processing` has no caller; `BANK_STATE_MAP` maps only to terminal states) — they go Submitted→Completed — so the TP/SVB window is effectively `Completed` (money confirmed gone), which also catches the non-atomic complete! window. Excluding a window fails safe (under-explain → needs_review, never false-settle). New `pending_outgoing_payment` STATSD metric (rows/past_critical OP-scoped) in difference_service.

**SVB-routed OPs are excluded by design (correct, not a bug):** `route_through_svb!` moves TP→SVB via a `FUNDS_MIGRATION` forwarding Transfer (collected by the existing migration path → `explained_by_pending_migration?`) then repoints `egress_sub_account` to the inactive SVB sub. SVB sub-accounts aren't balance-checked at all (`DifferenceService#should_run?` returns false for `svb?`; SVB reconciles via BAI2). So the SVB leg is handled elsewhere and never surfaces as an unexplained break on a checked account.

**Truncation caveat:** `MAX_IN_PROGRESS_DETAILS = 200` in DifferenceService truncates the persisted column by descending `|adjustment_cents|`; all zero-adjustment rows (classify-only credits + these OP debits) tie last, so a >200-row account can drop them → fails the settle closed (safe under-explain → needs_review, never masks a break). Pre-existing BANK-1847/1557 behavior.
