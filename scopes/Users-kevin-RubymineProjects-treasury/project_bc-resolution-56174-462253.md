Investigation 2026-07-22 (bloom session). Kevin's 3 Qs about balance-check **resolution** for CA 56174 & 462253.

**`resolved` field semantics (verified `record_type.rb:111-121`):** computed LIVE on every read = `current_difference.zero?` (current_treasury − current_external, both fetched live). It does NOT read stored `discrepancy_amount` and does NOT consult `resolution_status` — the two are independent (a record can be `resolved:true` yet `status:needs_review`, or vice-versa). If live-zero + status nil, self-stamps `naturally_resolved` on read. ⇒ **No new run needed to DISPLAY resolved**; reload re-evaluates. A new run only re-mints a record + (flag `balance_check_auto_heal_inactive_subaccounts` ON) runs `ResolutionService.attempt_resolution!` which can create a migration transfer for stranded *inactive-SA* funds.

**Classifier GAP identified:** `RESOLUTION_EXPECTED_TO_SETTLE` covers only incoming credits (`explained_by_pending_activity?`) + funds-migrations (`explained_by_pending_migration?`). A stuck cross-account **ACCOUNT_MERGE** debit (category `TRANSFER`, `funds_migration=false`) fits neither, and `migration_past_critical?` only escalates `funds_migration` rows ⇒ stuck merges sit at `status=nil` silently, never `needs_review`. Proposed (awaiting Kevin): add past-critical escalation for stuck ACCOUNT_MERGE transfers mirroring `migration_past_critical?`. Do NOT teach the classifier to mark stuck merges `expected_to_settle` (would suppress a real problem).
