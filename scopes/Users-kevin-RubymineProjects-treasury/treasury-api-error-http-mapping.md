**SHIPPED pattern (PR #8389, branch `kevinliang/transfer-creation-error-409`, TREASURY-5G5):** treasury now has an extensible `HttpStatusError` mixin (`app/models/concerns/http_status_error.rb`, Sorbet-`abstract!`) — the REST analog of the Prophet layer's self-classifying domain errors (`TreasuryProphetApi::Errors::*` extend `Prophet::RequestError`). An exception `include`s it and implements `http_status` (Symbol or nil), plus overridable `error_code`/`report_to_sentry?` (default false). `Api::Controller` has ONE generic `rescue_from HttpStatusError, with: :http_status_error` (renders the declared status; nil defers to `uncaught_exception` = 500+Sentry). Base placement + module marker ⇒ every controller covered by inheritance (`rescue_from` matches modules via `is_a?`; register below `StandardError` so it wins). `Transfer::CreationError` is the first includer: `:conflict` when `account_missing_sub_account` present, else nil. **To map a NEW domain exception to a 4xx: `include HttpStatusError` + define `http_status` — no controller change.** Don't use a per-controller concern: `Transfer::CreationError` is raised transitively from ~25 service sites across many controllers (MMF buy/sell via OrderService, OutgoingWires, StandaloneBankings, Transfers, CustomerAccounts), so an opt-in concern silently regresses the ones that forget it.

Treasury legacy REST API (`app/controllers/api/controller.rb`) exception→HTTP mapping, for "should this be a 4xx/5xx?" questions:

- `rescue_from` chain (evaluated bottom-to-top, so StandardError written FIRST = last-resort): `StandardError → uncaught_exception` (500 + `ErrorTracker.error` → Sentry), `RecordNotFound → 404`, `RecordInvalid → 422` (but 409 when `SubmittableAch#binding_amount_limit_cents` — the ACH-over-limit "reroute via wire" signal, proto `Errors` body), `ArgumentError → 400`. `uncaught_exception` does `raise error if Rails.env.test?` (so a fall-through 500 path RAISES in specs — assert `raise_error`, not a 500 status).
- Add a specific handler by writing `rescue_from SpecificError, with: :handler` BELOW the StandardError line.

**`Transfer::CreationError` (`app/models/transfer.rb:39`) has TWO raise categories — don't blanket-rescue:**
- Benign retryable race: `transfer.rb:108/116` (`from/to_sub_account!`) raise WITH `account_missing_sub_account:` set (a CustomerAccount). Means the account isn't provisioned yet; `Transfers::V2::CreateService` (`create_service.rb:46-54`) auto-retries the sub-account request then re-raises. → correct as 409, skip Sentry.
- Genuine server fault: catch-all `rescue => e; raise Transfer::CreationError.new(request, e.message)` at `create_service.rb:56` (comment "Presented as a 500") wraps ANY downstream StandardError (deadlock, TP API failure, ledger bug) with `account_missing_sub_account` NIL. → must stay 500 + Sentry.
- Discriminate on `error.account_missing_sub_account.nil?`. Also inherited by other `Api::Controller` subclasses raising it: `transfers_controller.rb` (sweep_mirror_account), `standalone_bankings_controller.rb` (create_transfer).

**Why 409-vs-500 is caller-safe (verified 2026-07-28, branch kevinliang/transfer-creation-error-409, TREASURY-5G5):** sole caller is Venture. The `protip` gem client (`protip/lib/protip/client.rb`) maps ONLY 422→UnprocessableEntityError and 404→NotFoundError; EVERY other non-2xx (409 AND 500) raises the same generic `Protip::Error`. Nothing in venture branches on `response.code` for transfers. Self-healing = Sidekiq job retry on any raised exception (status-agnostic; ExecuteAchInvestmentWorker/ExecuteSpecificInvestmentWireWorker default 25, ClosingExecutionWorker retry:1). So changing a treasury REST error's status code does NOT change venture retry behavior — only the Sentry/Datadog 5xx signal. Trigger for the 11.5k events: LP investment funding into a freshly-created FBO/escrow account before its sub-account finishes provisioning. NATS/Prophet path (`app/handlers/`) does NOT inherit `Api::Controller` → REST vs Prophet error handling diverge.
