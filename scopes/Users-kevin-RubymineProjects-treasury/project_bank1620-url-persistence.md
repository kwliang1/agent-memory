BANK-1620 (PR #8210, `kevinliang/bank-1620`): the balance-checks admin tool (`frontend/app/(authenticatedRoutes)/balance_checks/page.tsx` + `frontend/components/BalanceCheckRecordsTable.tsx`) now persists `run`, `page`, all filters, and sort in URL query params. URL is the single source of truth: state derived from `useSearchParams()` each render (replaced local `useState`), so reload, shareable links, and browser Back/Forward all restore the view.

Kevin's product decisions (2026-07-12): (1) switching runs **carries** the filter/sort lens across runs, only `page` resets — replaced the old reset-on-run-change; (2) Back/Forward **supported** in-session; (3) verbose URLs fine (internal tool) — multi-selects persist full value lists.

Key implementation gotchas (all have regression tests):
- Clamp effect must be guarded on `pageData` — pre-load `totalPages` defaults to 1 and would snap a valid deep-linked `?page=N` to 1 on mount.
- Adapt `<Table>` (non-hook `WithTableProps` path) has NO controlled `sortDescriptor`, only uncontrolled `initialSortDescriptor` (mount-only seed). It calls the `sort` callback on mount. Fix: guard `handleSort` to only write the URL on a genuine change, AND include sort in the Table `key` so a URL-only sort change (Back/Forward) remounts and re-seeds the arrow.
- `updateParams` must accumulate on a `useRef` write-base (re-synced from `searchParams` on commit), not the render-scope `searchParams` snapshot — else two rapid interactions on different params drop the first (router.push doesn't update searchParams until commit).
- Validate `sortColumn`/`sortDirection` from the URL against allow-lists (else no sort); `page` via `Number.isInteger && >=1`.

Follow-ups (see [[worktree-ssr-auth-gap]]): page.tsx run logic has no unit test (bun mock.module process-global + no auto-cleanup contaminates a 2nd test file); covered by e2e only.
