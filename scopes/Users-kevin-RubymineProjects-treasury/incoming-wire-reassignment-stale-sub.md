Investigated 2026-07-30 (bloom session), treasury. Symptom: IncomingWire 316074 reassigned person-CA 463571 → IRA-CA 463586, but `sub_account_id` stayed at old CA's sub 511798.

**Root cause:** the reassign path writes ONLY `customer_account_id`. `Mutations::IncomingWires::AssignCustomerAccount#resolve` → `incoming_wire.update!(customer_account_id: ...)` (`assign_customer_account.rb:39`). Model's only sub-account callback is gated on `sub_account_id_changed?` (`incoming_wire.rb:244`), not `customer_account_id_changed?`. Same gap in sibling entry points: Prophet handler `incoming_wires_handler.rb:46`, REST `incoming_wires_controller.rb:46`. **Not IRA-specific** — generic to all owner_types; IRA incidental.

**Money is safe — `transfer!` self-heals via `original_sub_account`, NOT the `sub_account` column.** `IncomingWires::StateService.transfer!` reads `incoming_wire.original_sub_account` (`state_service.rb:50`); reconciliation branch at `state_service.rb:69` fires when `original_sub_account.customer_account != customer_account && customer_account.active_sub_account != original_sub_account`. `revise_ledger_entry_destination!` with two CustomerAccounts runs a **genuine Transfer V2** (`revision_service.rb:196,236`) moving funds old-sub → new CA's active sub. It's a settling bank transfer that must succeed, NOT a free ledger re-point. `transfer!` deliberately preserves `original_sub_account` (`state_service.rb:48-50`) — that's why 2,848 transferred wires legitimately have `original_sub_account.ca != current ca` (normal footprint of every reassigned-then-transferred wire, not stranding).

**`active_sub_account` def:** `CustomerAccount#active_sub_account` (`customer_account.rb:215`) → `SubAccounts::InfoService.active_sub_account_for_customer_account` = opened-not-closed sub, raises if >1 (`info_service.rb:107-116`). Differs from the `SubAccount.active` scope.

**Gotcha — hand-flipping `sub_account_id` on a provisioned wire is fund-safe but not harmless:** `set_original_sub_account_on_first_assignment` is `||=` (`incoming_wire.rb:428`), no-ops when original already set, so it does NOT change `original_sub_account_id`; transfer/return both source off `original_sub_account` (`state_service.rb:78,85,253`) so funds unaffected. BUT the incoming-credit SLA reads `incoming_wire.sub_account` to pick its processor (`payments/health/incoming_credits/evaluation_service.rb:17,29`) — a flipped column mis-evaluates the SLA while provisioned (monitoring-only).

**Sibling-sweep detector must key on `original_sub_account.customer_account != customer_account`** (NOT `sub_account.*`), else a hand-corrected wire escapes the predicate while its money + original stay stale. For 316074, only 1 non-terminal wire matched (itself); rest terminal.

**CRITICAL — repoint-on-reassign BREAKS balance-check (caught by domain review round 1, prod-verified 2026-07-30).** For a **Provisioned/Hold** incoming wire, the `sub_account` COLUMN is balance-check's "where the cash physically sits" key: `collect_confirmed_unledgered_wires!` → `IncomingWire.where(sub_account: active_sa, state: [Provisioned, Hold])` (`balance_service.rb:489`, guard :494-495); `incoming_wire_adjustment` → `customer_account.incoming_wires.where(sub_account: active_sub).sum(&:balance)` (`balance_service.rb:46,132`). Repointing the column BEFORE the cash moves (cash only moves at `transfer!`) creates TWO phantom mismatches per reassigned wire: (1) the new CA's active sub gets the wire in its adjustment set → internal inflated, no cash at bank → +delta, guard skips it → unexplained; (2) `collect_confirmed` on the OLD sub (where cash IS) no longer matches → the real +delta there is unexplained. Proven live on 316074 after Kevin's manual flip (511798→512580): IRA sub 512580 adjustment set=[316074] w/ $0 bank, old sub 511798 unmatched. **So a provisioned reassigned wire's sub_account pointing at the OLD sub is CORRECT (cash location); `customer_account` already reflects the new owner; `transfer!` moves cash & reconciles via `original_sub_account`.**

Fix: add `|| revision_transfer?` to the skip list at `app/models/transfer.rb:882` (alongside forced_by_user?/account_merge_transfer?/funds_migration_transfer?). 3 files +46/-4. **Design (built in build-mode, LGTM after 3 rounds).** Kevin's ops constraint flipped the call: ops keys off the *displayed* sub, so `sub_account` MUST follow the assigned CA. Resolution = semantic split: **`sub_account`** = ops-facing "account this wire belongs to" (repoint on reassign); **`original_sub_account`** = money-facing "where cash landed" (immutable until transfer; balance-check + all cash-location readers key on it). Parts:
1. `IncomingWires::UpdateService.assign_customer_account!` — shared assign path for the GraphQL mutation + Prophet handler + REST controller; repoints `sub_account` to new CA's active sub for non-transferred wires with `original_sub_account` set; NEVER touches original. Repoint is best-effort (rescues the >1-active-sub raise → logs+skips, so reassignment can't 500).
2. `transfer!` reassignment branch repoints `sub_account` when cash moves (matches merge/on-core branches). For **IRA destinations** it forces past the IRA/FBO rule (`validate_ira_transfer` transfer.rb:882) with `USER_OVERRIDE` + the initiating **User** (recovered from the TSMv2 Initiator: `type=='User'` → `User.find_by(id: initiator.id)`) + a force_note, ONLY when source is non-FBO AND `source.verified?` (USER_OVERRIDE also suppresses `origin_is_verified` transfer.rb:786, so gate on verified to keep it narrow). Non-user initiator → no force → guard blocks (fail-closed). Threaded `forced_by_user`/`force_note` into `RevisionService.revise_ledger_entry_destination!` (both default nil).
3. Cash-location readers migrated to `IncomingWire.with_funds_in_sub_account` scope (`COALESCE(original_sub_account_id, sub_account_id) <=> ?`, null-safe) / `funds_sub_account`: balance_service (incoming_wire_adjustment :46/:132, collect_confirmed_unledgered_wires! :489 + guard), incoming-credit SLA processor (evaluation_service.rb), Layer2 unprocessed-balance guard (layer2_service.rb:60), Alloy originator TP lookup (helper_service.rb:266 — treasury_prime_wire_id lives at the landing instance).
