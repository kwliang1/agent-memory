CA 465829 exception (2026-08-19, RCA'd by ember): "Origin CustomerAccount 465829 has insufficient balance. Balance: $0.00 Amount: $1,800,000.00" during `Bai2PreviousDaySyncFiles::ProcessingService.process_for_date!`. Files 1445 (ord 34469 concentration) / 1446 (ord 34473 disbursement).

**REAL ROOT CAUSE (Kevin caught the premise): there was NO returned wire.** The $1.8M in the disbursement file (1446) is an INCOMING wire (BAI2 code 195), text: `ORG:=FIFTH THIRD BANK FBO AL ADVISORS`, `BNF ID:=3301234473` (our SVB disbursement acct), `OBI:=SVB ROUTING FOR OUTGOING PAYMENT`. It is our OWN funds-migration wire (T233074, FTB sub 513803 → SVB sub 515062) arriving to fund OP #778's outbound wire. OP #778's real beneficiary is Deterrence Defense Inc (ExternalWireAccount 94218) — a genuine return would originate from THEIR bank, not our Fifth Third FBO.

**The bug:** `Bai2SyncFiles::WireProcessingService.process_rejected_outgoing_wires!` (wire_processing_service.rb:269-319) treats EVERY `INCOMING_WIRE`-code credit (codes 195/214, lib/bai2_constants.rb:344) on the SVB disbursement account as a returned outgoing wire, then matches it to a submitted/processing SVB `OutgoingPayment::Execution` by AMOUNT ONLY (:284-303). The svb_routing funds migration routes EXACTLY the wire amount to SVB, so its arrival credit ALWAYS amount-collides with the very OP it funds. Normally the OP has completed (left submitted/processing, so not in `submitted_svb_op_executions_by_amount_cents`) before the previous-day file runs → no match. OP #778 was still `submitted` (execution 841; outbound wire to Deterrence Defense not yet sent — not in this file), so it matched → false `on_execution_completed!(RETURNED)` → `return!`.

Guard that should have excluded it but didn't: `filter_dibs_internal_transactions` (processing_service.rb:68-70) only rejects text matching `/IT[a-zA-Z0-9]{8}/`; this migration wire's ref is `2026230000826200` (no IT marker).

**Downstream symptom (the visible error):** `return!` (state_service.rb:801-808, processing branch) reverses the funding plan while OP #778 still `processing`, so its own $1.8M earmark on egress 465829 zeroes `available_balance` (balance_computation.rb:84 PENDING_DEBIT_OP_STATES includes Processing; :137-146). Reverse of pos1 ivc_pull (T233070 465829→465828, plain TRANSFER, no force — create_reverse! forces only same_ca, funding_plan_step.rb:287-290) hits transfer.rb:813 → RecordInvalid. `process_for_date!` is one transaction (processing_service.rb:19) → whole day rolls back (incl legit $1.08M sweep); files stamped processed_at w/ error, no auto-retry (:16).

**DO NOT apply reject-first reorder** (my initial wrong rec): it would let the false return SUCCEED — wrongly Reject a live $1.8M payment, claw back its funding to 465828, fire a Failed event to Venture. The insufficient-balance error was an accidental guardrail.

**Correct fix = classification, not the reversal path.** Stop treating internal cross-bank funding-migration credits as returns. Strongest signal: incoming wire ORG is our own FBO (self→self, originator = known AngelList FBO/partner-bank acct). Alt: tag funds-migration wires with `IT########` DIBS internal ref so the existing filter catches them; or match returns by outbound bank reference (IMAD/OMAD) instead of amount. **Amount-only matching is the core defect** and will recur for any multi-bank-routed SVB outgoing payment still submitted/processing when its previous-day file runs. Any 2026-08-19 reprocess must NOT return #778.
