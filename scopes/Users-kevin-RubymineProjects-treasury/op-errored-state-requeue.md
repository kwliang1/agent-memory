**Q (Grace/BANK-1832 Slack thread, 2026-08-19/20): "how do I mark an OP as errored / put it in a state Grace can re-queue?"** OPs 1058 & 848 stuck in `processing` with a wire error; Grace (ops) wants an `errored` state to review + re-queue; UI won't let her.

**Findings (treasury `main`):**
- `OutgoingPayment` (TSM V2, `app/models/outgoing_payment.rb:143-172`) has **NO `errored`/`error` state**. States: queued, requested, in_compliance_review, awaiting_ops_approval, processing, held, completed, pending_return, returned, rejected, cancelled. Failure exits from `processing`: `reject→rejected` (:380), `cancel→cancelled` (:386). Bank error is *meant* to funnel to rejected/returned via `StateService.on_execution_completed!(adapter_state: ERRORED)` → private `return!` (`state_service.rb:798`; processing→Rejected, completed→Returned). The child `OutgoingPayment::Execution` DOES have a real `Errored` state.
- **Why stuck:** DIBS notification path routes only completed/returned/rejected to `on_execution_completed!` — **drops error/errored** (`app/public_api/treasury_app/notification_service.rb:229`). So `record_bank_state!` flips the *execution* to errored (+error_message) but OP handler never fires → OP frozen in processing. TP webhook path DOES propagate (`treasury_prime/webhook_service.rb:15`). = "Bug 2" in #8605.
- **Why UI blocks Grace:** `reject_via_frontend!`/`cancel!` raise "already submitted to bank" when `processing? && execution.present?` (`state_service.rb:242-243, 358-359`). Frontend actions = cancel/hold/unhold/pass_compliance_review/reject_via_frontend/approve_for_submission/route_through_svb (`transition_state.rb:12-23`). **No requeue/resubmit action for OP.**

**Requeue = fresh execution attempt, NOT a state change.** `processing` IS the retry-able state. `OutgoingPayment::ExecutionService.submit!(op)` (`execution_service.rb:21-58,93-100`; :95 "Errored is retryable but gets a new attempt") mints attempt #2 (`-2` token) & re-dispatches, IF `op.processing?` AND execution not in-flight (`IN_FLIGHT_STATES=[submitted,processing]`, :8-14). Errored execution isn't in-flight → works. If execution still submitted/processing, first `op.execution.record_bank_state!('errored', error_message:...)` then submit!. Oncall console action; verify funds/egress intact + wire won't self-settle (retry = 2nd dispatch).

**Reject path is a DEAD-END for re-queue (Kevin's instinct, confirmed):** running `on_execution_completed!(adapter_state: ERRORED)` → `return!` → OP `rejected` (terminal) + reverses funding + FAILED event. Then (1) same OP can't retry (`submit!` raises `if !processing?`, `execution_service.rb:35,100`); (2) a same-idempotency_token Venture retry **dedupes onto the dead rejected OP** and returns it untouched — `CreateService.create!` `find_by(idempotency_token:, shadow:); next existing if existing` (`create_service.rb:40-42`), rejected OP runs nothing post-commit → no new OP, no execution; (3) a fresh OP needs Venture to re-initiate with a NEW token (Venture-side, not treasury UI). So reject = "fail cleanly so Venture starts over"; **real re-queue = `ExecutionService.submit!(op)` retry-in-place** (keeps OP in processing, no funding reversal).

**Correcting bad details before re-send:** adapters read **live `payment.destination`** at submit (`svb.rb:7`, `treasury_prime.rb:28/81`, `dibs.rb:13/69`); `metadata['destination_snapshot']` (`create_service.rb:194-242`) is audit-only. So **Case A** (wrong acct#/ABA/name/address on the destination account) = edit the EWA/EAA record, then `ExecutionService.submit!(op)` sends corrected live values in attempt #2 (caveats: EWA may be shared; name-mismatch allowlist may re-trip; snapshot stays stale by design). **Case B** (wrong amount/category/origin, or need a different destination) = NO OP edit path (only mutations are ApplyReturnFees + TransitionState; no UpdateService, no re-point-destination) → must fail + Venture re-creates with new token. Rule: fixable on destination record → edit+submit!; fixable only on OP → new OP.

**DESIGN CONFLICT (Kevin to settle) — PR #8605 (BANK-1832, dcetlin, OPEN/not merged, branch `fix/op-execution-error-handling`):** first cut ADDED a real `State::Errored` (+ PENDING_DEBIT/DEQUEUED membership, state mappings, cancel/reject guards — all bot fixes applied), then **removed it**; final design = OP stays in `processing`, error only on execution + red "Processing (Execution Error)" tag + Flowdash `Execution Bank State`/`Execution Error` columns. Review bots flagged Grace's exact complaint ("stuck in processing, ops has no action"); Dan marked **intentional** (execution error ≠ payment failed; bank may resolve). This is the OPPOSITE of Grace's ask. Options: **(A)** ship #8605 as-is (no errored state; retry=reject+recreate or console submit!); **(B)** reinstate the `State::Errored` Dan already built (what Grace wants: prompted-review + requeue). Dan's "ops resolves via manual intervention" = the `ExecutionService.submit!` console call above.

**"Generalize error-as-derived-state into a concern?" (Kevin, 2026-08-20):** Premise is N=1. Only **OutgoingPayment** derives an "errored" *display overlay* from a column (child `execution.bank_state`/`error_message`; OP FSM has no errored state — intentional per #8605). Every OTHER transfer model has a **real** `errored` FSM state: OutgoingWire (`treasury_prime_errored`+`submission_error`), Transfer (`Errored`+`metadata.error_message`), AchPush/AchPull (`errored`/`needs_admin_attention`+`return_code`/`ach_error_at`), Book/Network/Cross. So NOT a shared-concern candidate for the state derivation. Real mess is *within* OP: overlay re-derived in 2+ sites w/ different predicates — resolver #8605 `execution.bank_state.in?(%w[error errored])` (`op_state_display_and_intent`) vs composite callout `exec.state==Failed/Errored` (`outgoing_payment/display/composite_callout_service.rb:143`); Flowdash dumps raw cols; and `treasury_events/transfers/info_service.rb#mapped_state` reads only `op.state` → errored OP maps to Processing, **drops the error signal**. My rec: (1) consolidate onto `OutgoingPayment#error_overlay` {display,intent,detail}, all 4 surfaces call it; (2) promote to a hook on the EXISTING `TypedStateMachineV2::Display` concern (`lib/typed_state_machine_v2/display.rb`, already has `state_color_map`/`composite_callout`) when model #2 needs it — NOT a new concern. Separately, a small `HasBankError` reader concern IS justified now (error-detail cols inconsistent: error_message/submission_error/rejection_reason/bank_state/return_code/ach_error_at); dovetails w/ standing "shared bank-state vocabulary" TODO at `outgoing_payment/execution.rb:185`.

**Adversarial-review corrections (2026-08-20, verified in code) — supersede loose claims above:**
- **NO automated terminal path for a processing OP.** Only terminal path = `OutgoingPayment::StateService.on_execution_completed!`, called from 3 bank sources only (notification_service/DIBS, webhook_service/TP, bai2_sync/SVB). `find app -iname '*reap*'/'*timeout*'/'*stale*'` empty. So #8605's non-terminal errored OP is **permanently non-terminal**.
- **stale-processing gauge is an ORPHAN.** `Payments::Health::MonitorJob#emit_stale_processing_op_gauges` (monitor_job.rb:172-188) detects exactly the errored-execution shape (processing OP + completed funding_plan + no in-flight execution) at 30min and emits `outgoing_payment.stale_processing.{count,max_age_minutes}` — but `grep -rin stale_processing ops/datadog/` = NO monitor AND not on any dashboard. Nearest monitor `outgoing-payment-stuck-requested.json` watches Requested stage, not Processing. So #8605 errored OP = no terminal state + no downstream TreasuryEvent + no human page (treasury-fatal-incident-automation-gap pattern). FIX: wire a monitor on the stale_processing gauge.
- **DIBS `errored` is RECOVERABLE, not terminal** (`backend/dibs/app/models/dibs/payment_transfer.rb`): `event :error` = provisioned→errored (line 155, pre-submission); `event :process` = errored→processing (line 140, retry); notifies treasury on every state change (line 112). No DIBS `error` state (that's TP's string). DIBS genuine terminal failures = rejected/returned/cancelled, ALL already routed. ⇒ **"Bug 2: DIBS errors silently dropped" is suspect** — dropping recoverable pre-submission errored (bank_state-only) may be correct. Routing DIBS errored → legacy `return!` would terminalize a state DIBS retries (funds released, Venture told FAILED) = worse merge-day bug. #8605's own new stay-processing semantics are safer for DIBS here. BUT errored→processing is a manual/cron `process`, not automatic → PT can strand in errored (explains OPs 848/1058 stuck) ⇒ real remediation may be at DIBS retry layer.
- **#8605 bugs (fix by gating display on current state, NOT nulling history):** #4 `execution.error_message` never cleared on completion (record_bank_state! only assigns when present, execution.rb:259) → stale in Flowdash 'Execution Error' col on completed OP; correct fix = gate col on `bank_state.in?(%w[error errored])`. #5 `rejection_reason: nil` clear on COMPLETED guarded by `.present?` not `processing?` → a late/dup COMPLETED on already-rejected OP nulls reason w/o transition (audit regression); fix = move clear inside `processing?` branch. Both: columns=history, display=gated, nothing nulled — indicts #8605's existing rejection_reason clear too (overloads a "terminal reason" col as transient scratch). #6 unrelated SVB-TAG frontend callout = scope creep, split out. #7 `record_bank_state!` (unconditional) vs `on_execution_completed!` (gated on adapter_state.present?) diverge on off-map status → fix = shared record+route GATE, not a shared vocabulary.
- **Generalization answer ("should it be a concern?") = NO.** N=1 (only OP derives; 6+ siblings have real errored states); wrong question. If Kevin lands terminal (likely, per Grace), OP gets a real errored state like siblings and there's no overlay to abstract. Only cross-cutting item worth a small concern = error-detail-column reader (names inconsistent: error_message/submission_error/rejection_reason/bank_state/return_code/ach_error_at), gated on current state.
