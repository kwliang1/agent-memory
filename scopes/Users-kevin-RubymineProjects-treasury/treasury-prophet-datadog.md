For verifying treasury Prophet handler behavior in Datadog:
- **APM spans**: `service:treasury-prophet`, `operation_name:prophet.process`, `resource_name:treasury.<handler>.<action>` (e.g. `treasury.customer_accounts.create`, `treasury.aba_routing_records.show`). `status:error` / `status:ok`. Error type at `@error.type`.
- **Canonical pre-sampling metric** (what the dashboard widgets use): `trace.prophet.process.errors` and `trace.prophet.process.hits`, tagged by `resource_name`, `env`, `service`. Prefer this over sampled span counts for rare-event verification.
- **Banking dashboard**: id `yhb-gss-6j5` (title "Banking"), section **API – Prophet** — Prophet Errors list (`!status:ok`), Errors-Per-Resource, Availability SLO. Banking monitors: "[Banking] Prophet API Error Rate Elevated", "[Banking] Prophet API Absolute Error Count Spike".
- **Banking dashboard "GraphQL Errors" panel** (section *API — GraphQL*): a `trace_stream` (APM) list, `query_string: @_top_level:1 service:treasury-graphql !status:ok $env` — reads **error spans**, NOT logs, and `service:treasury-graphql` (the graphql-exec span), NOT `service:treasury-web` (the rack/HTTP span). Metric widgets use `sum:trace.execute.graphql.hits/.errors{service:treasury-graphql,$env}`. **The panel + metric widgets are BROKEN — blind to ~92-96% of real graphql errors (proven 2026-07-30).** Root cause: graphql-ruby's DataDog tracer records the error on the INNER child span (`operation:execute_query`/`execute_field`, `resourcename:execute.graphql`), while the TOP-LEVEL treasury-graphql span (`operation:execute_multiplex`, resource = the operation name e.g. `CreateOnCoreAccountMutation`) stays `status:ok` (error never propagates up). So `@_top_level:1 !status:ok` matches NEITHER (errored span isn't top_level; top_level span is ok). Same reason `trace.execute.graphql.errors` metric under-counts (trace metrics only emit for top-level/measured spans). Evidence (4d, env:production): `service:treasury-graphql status:error`=142; panel query `@_top_level:1 service:treasury-graphql !status:ok`=12; `trace.execute.graphql.errors` metric=6. Fix = drop `@_top_level:1` (use `service:treasury-graphql status:error`) or a span-based error metric. **Where graphql errors DO surface**: APM **Error Tracking** (issue id on the error span, e.g. DataValidationError issue `b313d376-…` recurring since Apr 2026), **Sentry** (StandardError catch-all→ErrorTracker.error→capture_exception; `error.handling:handled`), and the user's response `errors[]` (HTTP 200). Example: `CreateOnCoreAccountMutation` failing `incorporation date required for on-core accounts` (create_service.rb:545, fund-application path) returns rack 200 but execute_query span status:error — invisible in the Banking GraphQL panel. Separately, the ORIGINAL log Kevin linked was a treasury-web "Completed #execute" `status:200/level:info` info LOG (only in Logs Explorer, `@payload.params.operationName` is a log attr) — even a truly-failed graphql req logs rack 200 because GraphQL 200s with in-body errors.
- **Treasury GraphQL error pipeline** (`app/graphql/graphql_schema.rb:17-53` rescue_from chain + `lib/error_tracker.rb`): every resolver error → `GraphQL::ExecutionError` → response top-level `errors[]`, HTTP **200**, field null (user/Apollo DOES see it). THREE tiers, and 2 are invisible server-side: (1) `ActiveRecord::RecordNotFound`/`RecordInvalid` → msg only, **NOT** Sentry, **NOT** DD span-marked (hard-suppressed via `DATADOG_SUPPRESSED_ERROR_CLASSES` error_tracker.rb:7); (2) typed "expected" (`SWIFT MissingBank/Branch`, `OutgoingPayment::InvalidStateError`) → msg + `extensions.code` for FE deep-link, also NOT Sentry/DD; (3) `StandardError` catch-all → `ErrorTracker.error`→`Sentry.capture_exception` + `span.set_error` + `Datadog::Tracing.keep!` (error_tracker.rb ~64,113) → shows in Sentry AND APM. Raising `ExecutionError` alone does NOT trip the DataDog graphql tracer (caught by graphql-ruby, never propagates). ⇒ "not in the GraphQL Errors panel" ≠ "user had no error." `CreateOnCoreAccount`'s main failure `raise 'No investment vehicle configuration found'` (create_on_core_account.rb:37) is a bare StandardError → visible; but a bad account id (RecordNotFound) surfaces to user yet is invisible in Sentry+dashboard.
- **env gotcha**: filter `env:production` explicitly — staging is very noisy (thousands of errored `customer_accounts.details` bulk/`RecordNotFound` spans). Image tags read `production-<sha>` even on staging spans, so don't infer env from image_tag.
- Bulk handlers (details/balance/ledger) always marked span errors via `bulk_process_ids`; the non-bulk direct path only started marking INTERNAL_ERROR faults after PR #7965 (merged 2026-06-26).
