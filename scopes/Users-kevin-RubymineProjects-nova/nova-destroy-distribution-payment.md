Destroying a nova `DistributionPayment` + linked `Payment` from `NOVA-GRAPH:PRODUCTION` REPL (schema in `packages/prisma/models/banking.prisma` + `distribution.prisma`):

**Payment side has NO cascades — all `onDelete: Restrict`.** `PaymentTransfer`, `PaymentEvent`, and `DistributionPayment` all reference `Payment` with Restrict, so the Payment won't delete while any child points at it. Delete children first, in order:
1. `DistributionPayment` (unblocks Payment's Restrict FK)
2. `PaymentEvent` where `paymentId` (covers payment- and transfer-level events; both Restrict)
3. `PaymentTransfer` where `paymentId`
4. `Payment`

**DistributionPayment side self-cleans:** `DistributionNoticeNotification` = `onDelete: Cascade`; `DistributionDraftPayment.linkedDistributionPaymentId` = `onDelete: SetNull`. Both handled at DB level (postgres relationMode=foreignKeys) when the DP is deleted — no manual cleanup.

**Safety gate:** a staged payment shows `requestedAmount`/`completedAt: null`, DP has no `verifiedAt`/`approvedAt`/`recipientConfirmedAt`. If any `PaymentTransfer` has a `transferId` or `completedAt`, the transfer was actually initiated in Treasury → deleting orphans real money movement; refuse. Wrap the deletes in `prisma.$transaction` with a guard that throws on `transfers.some(t => t.transferId || t.completedAt)`.

Status is DERIVED from timestamps (never cached): DistributionPayment STAGED→RECIPIENT_CONFIRMED→VERIFIED→DISBURSED; Payment completed/cancelled from timestamps. Related: [[nova-prod-db-access-from-bridge]] (I can't reach nova prod DB — hand Kevin the REPL script).

**Lesson (capture-before-delete):** in the verify/destroy result tables, include the recipient key (`directoryEntityId`) and any FK you'll need later — NOT just dpId+paymentId. Hard delete is irreversible; I had to reconstruct the 8 destroyed recipients afterward via orphaned drafts: `DistributionDraftPayment` where `allocationAmount=0, publishedAt!=null, linkedDistributionPaymentId=null` (the SetNull'd link) → `draftDirectoryEntity.linkedDirectoryEntityId`. That came back null for all (draft entities unlinked), so emails had to be cross-mapped by name against surviving recipients.

**Recipient email path:** `DirectoryEntity → directoryPersonToDirectoryEntityLinks → directoryPerson.email` (schema `directory.prisma`). Dedup-check for "will recipients see duplicate transfers": `distributionPayment.findMany({where:{distributionId}})` grouped by `directoryEntityId`, flag count>1.

**REPL gotcha:** in a shared/persistent NOVA-GRAPH REPL, wrap each script in `await (async () => { ... })()` — top-level `let x` collides across pastes ("Identifier already declared"). `prisma` is preinjected.

**Resuming payout on a real DP (money movement):** the initiate cron (`graph/src/cron/jobs/initiateDistributionPayments.ts`, every minute) auto-sends any DP with `recipientConfirmedAt` + `approvedAt` + `approvedById` + a recipient VBA pinned on the Payment (`payment.recipientVirtualBankAccountId`) + (VBA payments) the connected entity Treasury-KYC-verified. So making a DP eligible pays it within ~60s — no manual send. DON'T raw-stamp: the VBA must be the entity's *primary* bank VBA (`virtualBankAccount` where `entityFinancialAccount.{entityId, accountType:BANK}`, primary = `purpose==='PRIMARY'` else oldest), and the cron independently re-checks Treasury KYC so faking `verifiedAt` won't pay a non-KYC'd entity. Correct resume = invoke `services/distribution/payments/confirmRecipientDistributionPayment` (pins VBA, confirms, claims verification via real Treasury check, auto-approves only if already GP-approved OR org sfr3, else stays STAGED) then GP-approve. **VBA-payment prisma-mirror equivalent** (confirmed: `approveAndLockPayment` → plain `setApproved` for VBA, no snapshot/EEBR-lock; `initiate()` writes the frozen account payload itself): per DP, `payment.recipientVirtualBankAccountId = <primary VBA>` + `distributionPayment.{recipientConfirmedAt:now, approvedAt:now, approvedByIntegrationId: NOVA_INTEGRATION_ID='44ce36fc-7a41-41e5-bf3b-d3cab2a66f44'}`. Leave `verifiedAt` null — the cron re-checks Treasury, don't fake it. **For the CF incident the ask was recipient-confirmation ONLY** (Jack Plank: "GP has not approved and FAST is not signed off yet") — so restore only `recipientConfirmedAt` + pin the VBA, do NOT set `approvedAt`/`approvedBy`. GP approval + FAST compliance sign-off is a separate gated process; without `approvedAt` the initiate cron never fires (no money moves). Must still pin the VBA (approval doesn't pin it; a confirmed DP with no destination fails later). The deleted dummies' Datadog `approvedAt=Y` was NOT the real GP approval. `findReadyToInitiate` gates on recipientConfirmedAt+approvedAt+approvedBy{Account,Integration}Id+paymentId+requestedAmount>0+no live PT; cron `filterEligiblePayments` adds the per-connected-entity Treasury KYC check. Recover deleted-DP state (which recipient/verified/approved flags) from Datadog `service:nova-graph` logs by dpId.

**"Awaiting approvals" needs a TransferControl, and raw-DB confirm never creates one.** The pipeline UI "Awaiting approvals / 0 of N" state requires a `transfer_control_v1` row (frontend `buildStatusLabel`: no control → "Awaiting transfer setup"; control present → "Awaiting approvals"). The control is created by `services/distribution/payments/initiate` (PaymentTransfer + Transfer + TransferControlV1 `CREATED`), which is invoked by `approveAndInitiateIfEligible` — and that is ONLY triggered synchronously by recipient actions (confirmRecipientDistributionPayment / selectExternalBankReference / submitExternalBankDetails / submitEntityKycForm), **never by any cron**. The one cron (`initiateDistributionPayments`) only `initiate()`s payments already `approvedAt`-set. So reconstructing a payment via raw DB writes (recipientConfirmedAt/verifiedAt) leaves it stuck with no control, and nothing auto-fixes it — you must run `await (await import('services')).distribution.payments.approveAndInitiateIfEligible({ distributionPaymentId })` yourself. `approvedAt` is a **legacy auto-set field superseded by the control** (`autoApprove` sets it to `distribution.createdBy`) — NOT the GP approval; the real GP+FAST gate is the control's reviews. So creating the control auto-sets approvedAt yet leaves it "0 of N approvals" (unapproved). `initiate()` does NOT move money — it stores the Treasury payload and defers the Treasury call until the control clears. A CANCELLED transfer with `paymentExists:true` is NOT an orphan (a real prior/cancelled record); only `paymentExists:false` is orphaned.

**Bank-account-on-wrong-entity port (CF 2018 dist fallout):** when the deleted $0 dup was the entity that KYC'd + opened the bank account (EntityFinancialAccount + treasury CA), the survivor payment's connected entity is bare (no VBA, `alIpseityEntityId: null`). To fix, PREFER re-pointing the survivor `DirectoryEntity.connectedEntityId` to the KYC'd/banked entity — do NOT just flip `EntityFinancialAccount.entityId`: the treasury CustomerAccount is KYC-*owned by a specific entity at Treasury*, so a Nova-only move desyncs Nova vs Treasury ownership and the payout cron's per-connected-entity Treasury KYC gate fails on a non-ipseity entity. A recipient can have ≥3 entities (survivor-connected / dup-connected / bank-account-holder) — map the graph (each entity's `alIpseityEntityId`, EFAs, VBAs, connected directory entities) before porting. Sky report `cf-dist-report.html` (session ff906fb2) documents the incident.

**Downstream cost of deleting a "past-STAGED" $0 row:** if a destroyed $0 DP had `recipientConfirmedAt`/`verifiedAt`/`approvedAt` set (the recipient had *accepted* on the duplicate entity), that acceptance is gone forever and the recipient's surviving real payment shows Pending — needing re-acceptance. "Accept" = `recipientConfirmedAt`; but the real flow (`services/distribution/payments/confirmRecipientDistributionPayment`) also pins the recipient VBA on the Payment, sets `lpSelectedEebrId`, emits an event, and `approveAndInitiateIfEligible` (can create a transfer). A raw `prisma.distributionPayment.updateMany({ data: { recipientConfirmedAt: new Date() } })` is SAFE (no money moves — skips approve/initiate) but INCOMPLETE (no VBA/EEBR pin); diagnose `payment.recipientVirtualBankAccountId` + `directoryEntity.connectedEntityId` first. LP-status Pending/Confirmed derives from `recipientConfirmedAt` (see `data/distributions/paymentPipeline.ts`).
