Running the nova app in a `just worktree-init` env for UI verification/screenshots (repo skill `.claude/skills/worktree-dev/SKILL.md`).

**On any nova worktree task — especially a resurrected/fresh session — reach for the repo's codified tooling FIRST: the `worktree-dev` skill + `just worktree-init`. Do not hand-roll `git worktree add` + `pnpm install`.** A bare checkout is missing gitignored prereqs (`.npmrc` GHPR auth, `.devcontainer/.env` from SOPS, codegen artifacts) so `tsc`/tests fail confusingly (Kevin flagged this 2026-08-05). **Why:** it codifies auth/env/codegen/DBs/ports. **How to apply:** for a *new* branch `just worktree-init -n <name> [-b <branch>]`; for an *existing* branch the init recipe can't attach (it always `-b`'s a new branch off HEAD) — so `git worktree add .worktrees/<name> <existing-branch>` then infra-only `cd .worktrees/<name> && just worktree-init` (no -n).

**Validating a worktree: use `just lint-types` / `just test`, NOT `pnpm --filter ./graph lint:types` directly.** The turbo `lint:types`/`test` tasks `dependsOn ["codegen","^build"]`; a direct pnpm filter skips `^build`, so every workspace package import (`@angellist/nova-prisma`, `@angellist/nova-core/*`, `nova-authz`, `nova-vulcan-*`) throws spurious `TS2307 Cannot find module` — not real errors, just unbuilt `dist/`. `just` also loads the `.devcontainer/.env` dotenv that codegen needs.

**Headless screenshots are blocked by real AngelList SSO.** The dev app redirects unauthenticated to `angellist.dev/v/login`, and `angellist.dev` 502s from a spawned/sandboxed session (external network wall). The `_angellist_v2` session cookie is a **live bearer credential validated against Venture** (`graph/src/lib/datadog/traceUser.ts`; `ANGELLIST_SESSION_COOKIE_NAME` in `graph/src/lib/config.ts`), **not** validated locally — so you cannot mint one offline. Both comet (NOVA-3718) and pixel (NOVA-3680) hit this. The portal domain (`portal-<name>.angellist.dev`) also doesn't resolve from the sandbox (works in Kevin's browser). Two real options: (1) hand Kevin the worktree URL + click-path and he screenshots in his authed browser; (2) wire the **nova-e2e emulator** — point the app's `VENTURE_BASE_URL`/`AUTH_BASE_URL`/`INTERNAL_VENTURE_BASE_URL` at it and inject the cookie `new AuthCookie({id: ventureId, email}).toString()` from `@angellist/nova-e2e-emulator` (see `nova-e2e/tests/utils/browser-context.ts`); higher effort + must align emulator users with the cloned dev data. Kevin rejects ADAPT-mockup artifacts — he wants the real local app.

**Base a worktree off current `origin/main`, not stale local main.** `scripts/worktree/init.sh` does `git worktree add … -b <branch> -- HEAD`, i.e. branches off local main (was 114 commits behind). Instead: `git fetch origin && git worktree add .worktrees/<name> -b <branch> origin/main`, then run **infra-only init** inside it: `cd .worktrees/<name> && just worktree-init` (no -n/-b → skips the git step, still copies env, installs, prisma-generate, clones dev DB from main postgres, nginx, ports, `.worktree-context.md`).

**Build-churn kills the running graph dev server.** `just codegen` / `just lint` / `pnpm build <pkg>` share turbo with the `just dev up` graph process — running them concurrently SIGTERMs graph (process-compose marks it `Completed`, app then shows `fetch failed` on :graph-port). Restart: `curl -X POST http://localhost:<PC_PORT>/process/restart/graph`. Also: a fresh worktree often needs `pnpm run codegen` in `graph/` (proto gen — `proto/gen/services/*` missing else "Cannot find package 'proto/gen/…'") and `pnpm build` of `@angellist/nova-logger`/`nova-core` before DB-backed graph tests load. The GraphQL SDL `graph/schema.graphql` is dumped by `graph/scripts/dump_schema.ts` (`pnpm run schema:dump`), which `just codegen` does NOT run — run it after adding a Pothos enum value, then `pnpm codegen` in `app/`. `schema.graphql` + `app/gen` are gitignored (CI regenerates).

**Docker + `just worktree-init` DO work in a spawned session — don't give up on them.** (Corrected 2026-08-08: Kevin caught me falsely claiming "docker down." Root cause was MY errors, not the env.) Pitfalls that misled me: (1) a one-off `docker ps` hung ~120s → I over-concluded "docker down" — recheck with `timeout 20 docker ps`, it lists running containers (banking_pg, ipseity-app-1, graph DBs; server 29.x). (2) Backgrounding `just worktree-init` from the **main-repo** cwd, or self-redirecting its output, produced empty logs / exit-144 deaths. The fix: `git worktree add .worktrees/<name> -b <branch> origin/main` then run **`just worktree-init` (no args = infra-only) IN the worktree in the background** and just wait — it completes in a few minutes (writes `.worktree-context.md` with ports). It is NOT fast-failing; my 90s foreground timeout killed a run that was mid-`pnpm install` (reached "line 542"). **So: real vitest AND Playwright e2e ARE runnable in a spawned session** — use the codified `worktree-dev` skill / `just worktree-init`, then `just e2e run --auto <filter>` (boots emulator+graph+app process-compose). Commit signing DID eventually work once Kevin unlocked 1Password (`%G?` shows `N` only because no local allowedSignersFile; `git cat-file commit HEAD | grep 'BEGIN SSH SIGNATURE'` confirms it's signed, GitHub verifies).

**Cloned worktree seed can be schema-stale → "Distribution not found" for EVERY distribution.** Verified 2026-08-11 (worktree recipient-treasury-link): the cloned dev DB's 8 seeded distributions all had `entity_financial_account_id = NULL`, but origin/main's Prisma schema now declares `Distribution.entityFinancialAccountId String` (non-null). So `data.distributions.findBy` → `findFirstOrThrow({ include: { organizationEntity: true } })` threw `Error converting field "entityFinancialAccountId" of expected non-nullable type "String", found null`, which `mapErr(() => NotFound)` turned into a 404 "Distribution not found" (FE renders the not-found NullState) for *every* distribution — looks like a routing/permissions/nav-flag bug but is neither (auth was fine; the `distribution(distributionLocator)` NOT_FOUND path fires before permissions). Diagnose via the graph dev log (`GraphQL execute error … [NOT_FOUND]`) + run `data.distributions.findBy` in a tsx script to see the real Prisma error. **Fix (local worktree DB only, disposable):** backfill the column — `UPDATE distribution d SET entity_financial_account_id = (select efa.id from entity_financial_account efa where efa.entity_id=d.sender_entity_id order by efa.created_at asc limit 1) WHERE d.entity_financial_account_id IS NULL;`. General lesson: when a cloned-seed page 404s/500s inexplicably, suspect a NULL in a newly-non-nullable column that a required `include` relation or scalar trips over — not the route/auth. (DB creds: user `nova`, pw from `docker inspect nova-<name>-postgres-1` POSTGRES_PASSWORD, port from `.worktree-context.md`.)

**Test DB isn't auto-created for a new worktree.** vitest points at `${POSTGRES_URL}_test` (e.g. `nova_<name>_test`); create + migrate it before DB-backed tests: `createdb … <db>_test` then `POSTGRES_URL=…/<db>_test npx prisma migrate deploy` from `packages/prisma`. See also [[treasury-local-dev-gotchas]] for the treasury analogue.

**Auth handoff needs local venture WARM, and it dies then recovers.** nova dev app (`portal-<name>.angellist.dev`) redirects unauth'd → `angellist.dev/v/begin`, which is Kevin's LOCAL venture (overmind: sidekiq/prophet/webpack/monolith/fundraising). If venture just started, `/v/begin` SSR-500s with `ApolloError: Received status code 500` (monolith/Rails still booting) — a blank page then the Next error overlay. Not broken: wait ~2min for monolith warmup and re-navigate; it then lands on the dashboard chooser ("Venture Admin"/"Venture User", logged in as venture@angellist.com). Don't shell-probe venture readiness on localhost:3000/3001 — routing is host-based (nginx→angellist.dev), so raw-port curls 404 misleadingly; the browser is the only real check. Clicking "Venture Admin" goes to venture's own admin app (`angellist.dev/v/admin`), NOT nova — to reach nova pages navigate portal-<name>.angellist.dev/<orgHandle>/accounts/<acctHandle> directly.

**The cloned dev DB can't drive the Transfer ("Send money") modal — both dropdowns come back empty.** Verified 2026-08-10 on worktree nova3740: nova DB creds = user `nova` / pw from `docker inspect nova-<name>-postgres-1` (POSTGRES_PASSWORD) / port 7828 / db `nova_<name>`. Org `asuna` (Asuna) is the main seeded org; sending account handle `asunacp-bank-account`; all EFA handles live in `entity_financial_account.handle`. In the modal, **Send-from Accounts = empty** (sendable-accounts query needs treasury-side customer_account linkages the clone lacks) AND **Send-to Recipients = empty** ("No available options. Type to create a new one" — the 9 `asuna` RECIPIENT `entity_external_bank_reference` rows have `organization_id=NULL` so the org-scoped picker returns nothing). All `/api/graphql` POSTs are 200 with empty data — no error. So the select-first repro (existing recipient → wire → edit acct → name clears) is NOT screenshot-able on this seed without cross-repo seeding; rely on the vitest unit tests + green CI, or the nova-e2e emulator which seeds its own data.
