Nova banking GraphQL mutations 403 with `GraphQLError: Forbidden` thrown at `graph/src/internal/schema/banking/externalBankReference/upsert/forEntity.ts:46` (via `lib/graphQLErrors.ts:30`). It's entirely a nova authz failure — treasury is NEVER called (the resolver short-circuits at the perm check before line 60's treasury call). Trace 272b1e6a… (2026-07-29) was all `service:nova-graph`.

**Authz mechanics:** `data/entity/financialAccount.ts:157-171` `hasPermissions` requires a `BankingPermission` row (with the requested flag `true`, e.g. `canManageFinancialAccounts`) hanging off the org member's *current* permission set (`organization_member.permission_set_id` → `permissionSet.organizationMemberUsingPermission`). Flag defaults `false` in schema (`banking.prisma` `BankingPermission`). It is NOT globally defaulted-on — granted `true` only by specific provisioning paths (invest-account sync `lib/venture/investAccounts/sync.ts:260`, org-entity create, portal get-or-create, KYC submit) or from admin input in the invite/edit flows.

**Confirmed root cause (Donald R. Kendall case, acct 6813ec6f/angellistId 55447, entity f29a9a05):** two compounding issues — (1) the acting user's permission set in the org the request was scoped to was created BEFORE `canManageFinancialAccounts` was auto-granted, so it has `canView=true, canManageTransfers=true, canManageFinancialAccounts=FALSE` (a missing-**backfill** gap, cf [[feedback-backfill-with-ledger-changes]]); (2) the entity lived in TWO orgs (old 2024 personal org + a newer banking org where the EFA + full perms were provisioned), and the mutation's `organizationId` input hit the org that lacked the grant. Fix: backfill the flag true on older sets that already have canManageTransfers, and/or disambiguate entity-in-two-orgs banking context.

**TWO EEBR-creation paths with DIFFERENT authz (the pivotal distinction):** (1) ON-PLATFORM withdraw — a recipient PAID on-platform (has an `EntityFinancialAccount`) links an external bank to withdraw proceeds → `upsertExternalBankReference`/`forEntity.ts` → REQUIRES `canManageFinancialAccounts` (org-member-level; resolver never consults `OrganizationEntityMember`). This is the 403 path. (2) OFF-PLATFORM payout — a distribution recipient submits wire/ACH details via `submitOffNetworkBankDetails` → `services/distribution/payments/submitExternalBankDetails` → authz is recipient-identity (`data.distributions.payment.hasPermissions` by accountId+email) + entity `canEdit`, NOT `canManageFinancialAccounts`; auto-connects the entity. So off-platform recipients need NO banking permission — only on-platform (EFA-holding) recipients hit the 403.

**RESOLVED for distribution `d_N9hYYPFL4x` (2026-07-29):** ran an idempotent Prisma REPL grant in nova prod console (Kevin ran it — bridge can't reach nova prod DB, see [[nova-prod-db-access-from-bridge]]). Scope: recipients whose entity has an EFA (on-platform withdraw cohort) → their org members lacking the flag, EXCLUDING internal AngelList staff (`@angellist.com` email OR `ninja` role). `granted: 34` (all idempotent flag-flip UPDATEs; `upsert` on `bankingPermission.permissionSetId` @unique; `update:{canManageFinancialAccounts:true}` only, preserving view/transfers; `create:{canView,canManage}` no transfers). Verified fan-out (30 EFA entities → 52 orgs) was benign dup-orgs (max 2 entities/org = no shared GP/fund-admin org). Actual observed impact was tiny (11 events / 3 sessions / 30d); the 34 was the latent EFA-recipient cohort. Donald handled separately (manual grant). OPEN follow-ups: RCA why the port DUPLICATED orgs + skipped the `canManageFinancialAccounts` backfill; and whether OTHER distributions need the same sweep (this fix was scoped to one distribution).

**Datadog scoping recipe:** `usr.id`/`usr.nova_id` live ONLY on the `express.request` span, NOT on any span carrying `@graphql.error.code:FORBIDDEN` — so you can't group errors by user directly. Use `@nova.session_id` (present on the `genericRequestHandler` error span) as a ≈user proxy, or correlate `trace_id` → the trace's `express.request` span for the user. Mutation input variables are NOT logged; entity/org/account IDs must come from a nova debug log line or the frontend payload. `graphQLForbiddenError` is generic — FORBIDDEN spans span many non-banking resolvers (data room, venture pass), so filter by banking `@graphql.operation.name` when sizing. Read ops (EntityFinancialAccountsForOrg, ExternalBankReferencesForOrg) gate on `canViewFinancialAccounts`, write ops (Upsert/Archive ExternalBankReference) on `canManageFinancialAccounts` — different flags, size separately.
