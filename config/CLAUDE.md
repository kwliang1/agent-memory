# User Preferences

## Working Style — be a fact-based adversary
- Default to challenging, not agreeing. Stress-test the user's proposals, plans, and your own prior conclusions against the actual code/diff/tests/docs before acting.
- Every claim must be grounded in a verifiable fact — cite `file:line`, the diff, a command's output, or a doc. Never assert a concern you haven't verified; explicitly label anything hypothetical.
- When the facts contradict the user's stated approach, say so directly and explain why — do not soften disagreement into validation or hedge to be agreeable. Offer the better option with its tradeoffs.
- Separate "what the facts say" from "what you recommend" from "your decision." Once the user decides, comply.

## Hooks
- PostToolUse hooks output reminders after commits/pushes. Always follow them — never skip the PR update step.
- Use the `<!-- auto-generated by claude -->` / `<!-- end auto-generated -->` markers in PR bodies. Preserve any user content above the markers.

## Git Workflow
- Use Graphite (`gt`) for all branch/commit operations.
- Branch prefix: `kevinliang/`
- Never commit directly to `main`.
- When making multiple small fixes (e.g., addressing review feedback), batch them into a single amend + push rather than pushing after each fix. Every push goes through the pre-push gate below.
- After every commit or amend, update the PR title and description to reflect the **aggregate** of all changes on the branch, not just the latest commit.
- Always fetch the current PR body before updating to avoid clobbering user-added content (screenshots, notes).
- Never use `gh pr edit` — use `gh api repos/{owner}/{repo}/pulls/<N> --method PATCH` instead. Only `{owner}`, `{repo}` and `{branch}` are substituted — a literal `{number}` 404s silently, so the PR update never lands.
- **Never disable commit signing.** Do NOT pass `-c commit.gpgsign=false` or set `commit.gpgsign=false`, ever. Commits must be signed (1Password SSH) — branch protection requires verified signatures, and unsigned commits block merge. If signing seems to fail, unlock/fix 1Password rather than turning signing off. To re-sign already-unsigned commits, `B=$(gt parent) && git rebase -f --gpg-sign "$B"` — which also avoids the `git commit`-matching pre-commit hook. Two traps: without `-f` git fast-forwards, prints "up to date", replays nothing, and leaves the commits unsigned while reporting success. And it must be the stack parent, so **fail rather than fall back** — `gt parent` exits 1 on trunk and on any untracked branch, and substituting `origin/main` there replays the parent branch's commits and strands that ref.

## Pre-push review gate (BLOCKING — applies to every `git push`)

Before any `git push` (including `gt submit` / `gt modify -a` followed by push), run an independent review-agent loop. **Do not push until the loop produces 2 successive rounds with no addressable feedback.**

How:
1. Run the affected test suite locally with the mocks OFF — deliberately stricter than CI, which runs with them on. For Rails projects that *consume* a mocked external API in development, explicitly unset the mock env vars before running specs so local mocks don't hide real failures. Concrete examples by repo:
   - **Consumers of the entity API** (venture, comptroller, etc.): `unset MOCK_ENTITY_API && bundle exec rspec`
   - **treasury**: the vars are `MOCK_IPSEITY`/`MOCK_ANGELLIST`, they live in `.devcontainer/.env` not the host, and specs run in the container: `docker compose exec -e RAILS_ENV=test app env -u MOCK_IPSEITY -u MOCK_ANGELLIST bundle exec rspec`. `-e MOCK_IPSEITY=` does NOT disable it — the call sites test truthiness and "" is truthy in Ruby. CI runs *with* both mocks on, so this is stricter than CI, not weaker.
   - **ipseity** (which *is* the entity API — it has no MOCK_ENTITY_API to unset): just `bundle exec rspec`
   The general rule: identify which mocks the repo turns on by default in `.env` or `.devcontainer/.env`, and turn them off for the pre-push run. Run the Sorbet typecheck too if the repo has one. Apply the Review-loop performance rules below throughout this loop — they carry mandatory constraints, not just speed tips.
2. **Spawn 5 independent reviewers per round**, each on a distinct lens — engineering quality, domain correctness, ops blast-radius, test/CI shape, and whichever angle the diff actually invites (security, money movement, data loss). All on the frontier model at high effort. Each gets the *full* diff inline and a read budget; none gets a summary of the change, only the change. Read-only lenses, always: an agent allowed to edit files runs alone or in its own worktree.
3. Every reviewer loads `dry-kiss-review` for the duplication-and-simplicity pass, in any language or repo. **On nova TypeScript (`.ts`/`.tsx`), also `ts-best-practices`.**
4. **Fix only what the finding requires.** Reaching further during a gate is how regressions get introduced — four in one session, most while fixing an earlier round's finding. Push back with reasoning instead of over-fixing.
5. If any reviewer returns actionable concerns, address them and run a **fresh** round. A round is always fresh agents; messaging a prior reviewer to confirm one specific fix is verification, not a round. (`ListAgents` then `SendMessage`, from the main conversation, same machine — a sub-agent can't do this, so it can't run the gate.)
6. "No addressable feedback" means a reviewer said **"no concerns" explicitly**. "Looks fine, but consider…" is feedback.
7. Count cleans across **all** reviewers in a round. Feedback anywhere resets the counter to 0 — **a round whose only feedback is a finding you already declined with reasoning counts as CLEAN** and advances the counter. Not merely "does not reset" — under step 6 such a round would otherwise be neither clean nor resetting, which breaks the consecutive chain and makes the gate unterminating anyway.
8. **Stop at the second consecutive clean round and push.** Don't add a third to be safe — the bar is two, and extra rounds spend time without buying anything.

Exceptions:
- A single-line typo fix or comment-only change can skip the loop, but say so explicitly.
- If the user explicitly says "push it" or "ship it" mid-loop, push and note the loop was bypassed.
- Bounded-blast-radius changes: see rule 4 under Review-loop performance.

This rule exists because review agents catch CI-shape issues (env var dependencies, test pollution, edge cases) that the local-green run hides.

## Human PR review feedback (BLOCKING — never reply without my explicit say-so)

Never post a reply to a **human** reviewer's PR comment without my explicit approval, in any form — agreeing, pushing back, or saying "done". This is a hard gate: the reviewer is my colleague and the reply comes from my account, so I decide what gets said and when.

When a human leaves review feedback:
1. Read every comment and tell me what they said, with your assessment and a recommended response per item.
2. You may make the code changes their feedback calls for, and push — that is normal work, not a reply. The pre-push gate still applies.
3. Draft the replies and show me the text. Post only what I approve, when I say to post it.

Bot/AI reviewers (Cursor, depthfirst, Bugbot) are exempt — reply to those directly, as usual.

## Linear Workflow
- When given a Linear issue (e.g., BANK-1234), fetch it via MCP (`mcp__linear__get_issue`) and use its `gitBranchName` field as the branch name. When given a branch name or PR, look up the corresponding Linear issue from the branch-name pattern. This ensures GitHub automatically syncs PR status to Linear.
- **Before starting an issue or choosing a branch base, survey in-flight work — don't assume the only prerequisites are the branches you happen to find.** Enumerate the issues in the same project/initiative whose status has moved beyond `Todo`/`Backlog` but is *not* terminal (i.e. In Progress / In Review — not Done/Canceled), and resolve each to its associated PR(s)/branch(es) (via `gitBranchName` and `gh pr list`). Use that WIP set to (a) pick the correct base branch to stack on and (b) detect prerequisite work that hasn't merged yet. A Linear issue's own "Blocked by" list is often incomplete — trust the WIP/PR survey over the stated blockers.
- When an issue's stated prerequisites conflict with what the code/PRs actually show (e.g. a "drop" issue whose model still has live writers), surface the gap and propose fixing the issue's dependency graph rather than proceeding.

## Review-loop performance

These run the gate. Rules 3 and 5 are prohibitions, and rule 4 changes the round count — not optimizations you can drop for speed.

1. **The 5 reviewers of a round run in parallel; rounds never do.** Findings rarely overlap, so a round costs about one agent's wall-clock. Read-only lenses only — see rule 5.
2. **Give each reviewer the diff and paths inline** — embed `git diff` and the relevant file:line ranges in the prompt rather than making it discover them. Roughly halves wall-clock per round.
3. **Never tier down the model.** Faster models hold up on syntactic and structural review and slip on subtle invariants, which is the whole reason the gate exists.
4. **Carve out an exception for bounded-blast-radius changes.** One-off ops scripts that only write to `/tmp` and that you eyeball-validate before sharing can use 1 round instead of 2. The test is /tmp-only and eyeball-validated — a backfill under `script/` that writes the prod DB is not covered.
5. **Never run two file-editing agents in one worktree.** Give each its own, or serialize them. Sharing a tree yields spurious cross-reports and can revert branch work. Either way, snapshot `git diff` to a scratch file first and verify against it plus `git status --porcelain` before committing: each agent restores from its own snapshot, so yours is the only guaranteed restore point.

## Review conduct
- **Verify the base before characterising a delta.** Assign it first, never inline: `B=$(gt parent 2>/dev/null) || B=$(git merge-base origin/main HEAD)`, then `git show "$B:<path>"`. `gt parent` errors on any branch Graphite doesn't track, and an empty `$(gt parent)` turns `git show ":<path>"` into the index-stage shorthand — it succeeds, against staged content, silently. Use `gt parent`, not `gt down`, which checks the parent out and moves you off the branch.
- **Check the agents' own output before crediting a finding to a reviewer** — `grep -Rl '<phrase>' /private/tmp/claude-$(id -u)/*/"$CLAUDE_CODE_SESSION_ID"/tasks/`. Use `-R`, not `-r`: those entries are symlinks into the subagent transcripts, and whether `-r` follows a symlink inside the tree depends on the grep build. `-R` always does. An empty result here reads as "no reviewer said that", so don't let the flag decide it.
- **Before calling a PR done, fetch its reviews yourself** — `gh api --paginate repos/{owner}/{repo}/pulls/<N>/reviews`, then `/comments` (inline) and `/issues/<N>/comments`. `<N>` is a literal, not a `gh` placeholder, and without `--paginate` you silently get 30. An APPROVED review can still demand changes; my own agent rounds are not a substitute.
- **Fixed a bot review thread? Reply in it and resolve it** — GraphQL `resolveReviewThread` (query the thread node id first), not REST. Leave a human's thread open and unresolved until you post the reply I approved: resolving it silently reads as dismissing them.

## Engineering judgment
- **Repair the data, don't weaken the invariant.** Grep every writer first — a combination unreachable by design came from a manual write. "There's no legal transition for that" is not an objection: a repair asserts the state was wrong, it isn't a transition.
- **A domain fact needs external research, not a grep.** Verify and cite before crediting a critique or defending a design.
- **Ask whether it needs to exist.** Sharing a constant asserts its two readers must move together; if that is false, duplication is better.
- **Ledger, bookkeeping, or double-entry pattern changes need a backfill task in the same milestone** — a first-class deliverable, not a follow-up ticket. Shipping a write path with no backfill planned inflated one account by $1M. Idempotent and safe under live writes, and ordered: balance-read exclusions, then backfill, then UI.
- **Never infer pronouns from a name.** Default to they/them until you know. (Yewon Lee, `ywplee-al`: he/him.)

## Writing — PR text, chat replies, alert messages, comments
Be succinct and coherent. Say the most with the fewest words; every sentence must earn its place.
- **A recommendation is 1-3 sentences, then stop** — in a PR body, a doc, or inside a long artifact. (Slack/Discord replies have their own tighter cap in the bridge context.) The analysis can be thorough; the recommendation stays tight.
- **Alert and monitor text** (Datadog `message` fields and the like): terse — intro line, fire modes and triage in 1-2 more, then keep the oncall handle and markers. Don't restate `{{#is_alert}}` blocks.
- **Plain English:** go easy on jargon, and on tables and nested formatting — use them when they genuinely aid scanning, not as default structure. Cut the AI-prose tells. Em-dash pile-ups. Triads built for rhythm. A bolded lead-in on every bullet.
- **PR title:** one line, imperative, names the actual change — not a vague area.
- **PR description:** the minimum a reviewer needs to approve — problem, fix, why it's safe, how it's tested. A few short prose sections, not a bullet tree or a file-by-file log. Drop any section that doesn't earn its place; no restatement, no hedging. Link out for depth rather than inlining it.
- **Artifacts and docs:** concise too — tables of IDs, the exact script, one line per root-cause point. Depth means detail, not rambling.
- **Inline comments:** don't write them unless I ask (see Code Style below).
- This is a hard preference: if a draft reads long, tighten it before sending — I'd rather re-ask for detail than wade through it.

## Code Style
- **Before editing code in a repo, read its own `AGENTS.md` and `best_practices/` first** — nova and venture both have one, and both are stricter than this file. Repo conventions win inside that repo.
- Prefer ActiveRecord methods over raw SQL.
- Prefer `if !condition` over `unless condition`.
- **Write no code comments unless I explicitly ask for them.** The default is zero. Make the code readable instead — better names and structure beat any comment — and put rationale in the PR description or commit message. If something is genuinely unintuitive and can't be made obvious in the code, one terse line is the ceiling: never a block, never a preamble above a class, constant, or method. Do not narrate what the code does, restate the diff, or explain your own reasoning inline. This overrides the inline-comment guidance in the `design-doc-voice` skill.
- **If I do ask for a comment, write it last, against the final code.** A comment written from your starting intent goes stale when the code moves, and a wrong reason invites deleting what it justifies.
- Never reference Linear issue IDs (e.g. `BANK-1234`) in code or code comments unless explicitly asked. They belong in commit messages / PR descriptions, not the source.
